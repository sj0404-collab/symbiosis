# Исследование обновляемого ядра — пока не рабочая функция APK

Цель: оставить лаунчер нативным и обновлять второе ARM64-ядро через доверенный канал без пересборки APK. Текущий APK закрепляет SHA-256 в `EngineLoader.kt`, поэтому произвольное новое ядро он не примет. Eden, JNI-мост, интерфейс и встроенные библиотеки находятся внутри APK; они не будут обновляться таким каналом без отдельной архитектуры. WASM-порт не создан; существующий Android `.so` нельзя исполнять как WASM.

## Прототип формата

`SignedCoreManifest.kt` проверяет только подпись RSA/SHA-256, строгий формат, пределы, минимальный номер и, отдельным вызовом, размер и SHA-256 файла. `sign_core_manifest.py` подписывает метаданные с указанным оператором ключом, не создаёт ключ и ничего не публикует. Тесты проверяют подмену, другой ключ, неправильный формат, ограничения, откат и совместимость Python/OpenSSL с Kotlin/JCA. Прототип **не подключён к загрузчику**, не имеет закреплённого production-ключа и не обновляет APK или ядра.

Пятистрочный ASCII-формат с LF, включая завершающий LF:

```text
SYMBIOSIS-KENJI-1
sequence=1
bytes=57321040
sha256=<64 lowercase hex digits>
signature=<base64 RSA signature>
```

Подписаны первые четыре строки, включая завершающий LF. Путь к файлу выводится только из проверенных номера и хеша, сам манифест не может указать произвольный URL. Пример: `https://github.com/sj0404-collab/symbiosis/releases/download/engine-test-1/libkenji-<sha256>.so`. Pages может раздавать **подписанный манифест**, файл ядра — отдельный версионированный release asset. Канал по замыслу тестовый; неизменность тэга/asset GitHub сама по себе не является защитой, фактический файл проверяется по подписанному хешу.

## Необходимые следующие шаги до APK

* Закрепить публичный ключ в APK, обеспечить хранение закрытого ключа и управляемую смену ключа; не класть закрытый ключ в git, Pages, APK или журналы.
* Проверять фактический файл в `.part`, ограничивать размер и соединения, проверять ELF/ABI/совместимость моста; ставить только после проверки в каталог приложения с защищённой от записи библиотекой. Не удалять работающую копию до успеха. Atomic commit и crash recovery тестировать специально.
* Защитить установку межпроцессной блокировкой на время запуска игры и проверки ядра; не менять файл под загруженным процессом. Проверить поведение при повторном `dlopen`, при ошибках, нехватке места и потере сети.
* Версии считать только по проверенной подписи и сохранять максимальную принятую версию с проверкой целостности, не обещая абсолютной защиты от отката после очистки данных приложения. Ручной откат — только в явно определённом, безопасном режиме.
* Реализовать нативные кнопку проверки/обновления, статус версии, результат и инструкцию. Не выдавать подпись/скачивание за доказательство работоспособности игры. Добавить закрытые локальные текстовые журналы с номером и хешем ядра, этапом и ошибкой; не писать ключи, содержимое игр или сейвы. Автоматическая публикация/отправка пользовательских логов не предусмотрена.
* Создать контролируемый workflow публикации, не заменяющий обычный релиз и старый asset; проверить артефакт и реально обслуживаемый Pages-манифест. Дальше host-тесты, CI APK и проверка на Android, включая сценарии отключённой сети, повторного запуска и падений.

До выполнения этих пунктов ни текущая сборка, ни данный прототип не дают обещанного обновления без APK. Известные SSL-заглушки и падение Account без PID не исправляются подписыванием.
