## 12. Плагины: правки без пересборки

Плагин — это правила, а не код, поэтому его можно проверить целиком на хосте: от текста
файла до «какие настройки уедут в ядро и какая пометка появится на плитке».

```bash
kotlinc tests/PluginEngineTest.kt \
  patch/android/utils/{PluginJson,PluginApi,PluginEngine,BuiltinPlugins,EngineHybrid,
                       NativeLibraryPresenter,LibraryIndex}.kt \
  -include-runtime -d pe.jar && java -jar pe.jar
```

```
passed=93 failed=0
```

Что держат эти 93 проверки:

```
ok   лишняя запятая названа словами
ok   повтор поля — ошибка
ok   слишком большая вложенность
ok   новая схема не принимается           [schema 99]
ok   опечатка в настройке названа с подсказкой  [«memy» → список допустимых]
ok   недопустимое значение настройки        [memory=999]
ok   ядро проверяется по имени              [«kenij»]
ok   массив — любое из                      [ext: [nsz, xci]]
ok   число меньше — не срабатывает на 8
ok   порядок списка не влияет
ok   при равном приоритете решает id
ok   одинаковые сообщения не дублируются
ok   важное наверху
ok   конфликт ядер замечен, победитель назван
ok   мусор в патче игнорируется
ok   действие на плитке не подменено
ok   пометка не повторяется дважды
ok   встроенный набор разбирается и применяется
ok   шаблон не срабатывает никогда
```

Три решения, которые эти проверки защищают:

1. **Массив значений — «любое из», а не «и».** Самая частая ошибка в таких форматах:
   `"ext": ["nsz","xci"]` не может означать «и nsz, и xci» — условие стало бы невыполнимым.
2. **Опечатка — ошибка загрузки.** Имя настройки сверяется с `EngineHybrid.FIELDS`, значение —
   со списком допустимых. «Плагин молча ничего не делает» хуже, чем «плагин не загрузился,
   вот причина».
3. **Порядок применения задан, а не случайно сложился.** Приоритет, затем id; при равном
   приоритете результат одинаков на любом устройстве. Конфликт не запрещён (общий набор +
   личный хотфикс — законная комбинация), но назван словами.

Run 41204815335, `24005c0f110e942353c3ef8608286033`, https://gofile.io/d/o1TY0dRF

```

ok   PluginEngine in dex
ok   PluginStore in dex
ok   string plugins_title is in the resource table
```

### Чего здесь нет и почему

Плагины **не могут исполнять код**: нет загрузки dex, нет shell, нет сети. Это ограничение, а
не недоделка — загружаемый код означал бы, что любой файл из чата получает права приложения.
Правил хватает на исходную задачу: плохо работающая игра почти всегда лечится настройкой,
ядром или честной пометкой «этот файл не откроется».

## 13. Папки, конвертер и след выхода

### Список папок: почему он терялся

Механизм был в коде, а не в «глюках». В `GameHelper.getGames()` стояло:

```kotlin
if (badDirs.isNotEmpty()) { ... gameDirs.removeAt(it - offset) ... }
NativeConfig.setGameDirs(gameDirs.toTypedArray())
```

Папка, у которой не подтвердилось разрешение, **удалялась из настроек и
записывалась укороченным списком**. Разрешение отзывается не только руками: система снимает
его сама после падения процесса. Дальше — ровно то, что видел пользователь: падение при
выходе из игры, следующий запуск, «осталась одна папка из четырёх». Вернуть остальные нельзя
было даже вручную: путь уже нигде не записан.

Плюс рядом стояло схлопывание «слоёв»: если `Games` и `Games/Switch` в списке, родитель
удалялся, и игры из его корня пропадали.

Что теперь:

| Было | Стало |
|---|---|
| нет доступа → папка удаляется | папка остаётся, помечается «нет доступа», нажатие возвращает доступ |
| родитель съедается вложенной папкой | обе остаются; дубликаты отсекаются по пути |
| список живёт только в конфиге ядра | вторая копия в prefs, пишется `commit()`, возвращает пропавшие |
| добавить папку — только в расширенной панели | кнопка «Добавить папку» на экране папок |
| убрать папку — только очисткой данных | долгое нажатие → «Убрать из списка» (с подтверждением) |

Проверки: `GameFolderListTest` — **34/0**, включая «одна битая строка зеркала не убивает
остальные» и «мелкий обход родителя не отменяет обход вложенной папки».

### Конвертер: почему не было ни уведомления, ни прогресса

Очередь распаковки жила в обычном `Thread` внутри процесса и складывала результат в
`files/converter` — приватную папку, невидимую ни одному файловому менеджеру. Уведомления не
было не потому, что забыли: его не могло быть, работа не была объявлена системе. Уход с
экрана → система прибивает процесс → распаковка обрывается на середине.

Теперь `ConverterService` — foreground-служба (`specialUse`, без лишних разрешений):
уведомление с текущим файлом, счётчиком и кнопкой «Остановить»; результат в
`Download/Symbiosis`; путь написан и в уведомлении, и в приложении; разрешение на
уведомления спрашивается в момент первой распаковки (без него на Android 13+ уведомление
не показывается вообще).

### Панель «видела не все игры»

Панель читала только кэш из настроек, нативный лаунчер — живой список. Два разных ответа на
вопрос «сколько у меня игр». Теперь порядок один: живой список, кэш — только если обхода
ещё не было.

### Краш при выходе

Причину не выдумываю: без журнала её не видно. Добавлен след — метки «запуск игры»,
«остановка эмуляции», «эмуляция остановлена», и отчёт в «Инструменты» → «Диагностика»:
время, шаги, и завершилась ли прошлая сессия сбоем (`previousSessionCrashed`). По этому
тексту видно, падает ли ядро внутри остановки или уже на возврате в библиотеку.

Само последствие сбоя — потерю папок — я убрал отдельно, и оно больше не зависит от того,
что именно упало.

## 14. Кнопка «Скачать ядро» и совместимость

### Почему кнопка не срабатывала

Три причины в одном месте, все — в `EnginesFragment`:

```kotlin
if (busy) return
busy = true
...
busy = false            // ← не выполнится, если корутину отменили
```

1. **Флаг залипал.** Скачивание идёт в `viewLifecycleOwner.lifecycleScope`. Уйти с экрана —
   корутина отменяется на `withContext`, строка `busy = false` не исполняется, и все
   следующие нажатия молча игнорируются до пересоздания экрана. Теперь `finally`.
2. **Плашка была не видна.** Прогресс и ошибки добавлялись в конец `root`, то есть ниже
   видимой части прокрутки. Нажатие «ничего не делало» — хотя сообщение было. Теперь плашка
   вставляется нулевой позицией, рядом с кнопкой.
3. **Кнопки могло не быть вовсе.** Она создавалась только при `EngineLoader.deviceSupported()`.
   Если проверка не проходила, карточка оставалась без действий и без объяснения. Теперь
   кнопка есть всегда: либо «Скачать (55 МБ)», либо «Скачать нельзя» и рядом — причина.

### Совместимость: что проверяется и чем это доказано

`DeviceCompat` проверяет три вещи и называет их по отдельности:

| Проверка | Плохо, если | Что говорит пользователю |
|---|---|---|
| архитектура | нет `arm64-v8a` | «процессор не arm64» + совет про официальный APK |
| разрядность процесса | `Process.is64Bit() == false` | «приложение работает 32-битным процессом» |
| страницы памяти vs ELF | 16 КБ страницы и `p_align < 16 КБ` | «ядро собрано под страницы 4 КБ» |

Разбор ELF и таблицы `auxv`/`AT_PAGESZ` — обычные функции над `ByteArray`, поэтому на них
есть тесты с синтетическими заголовками: `DeviceCompatTest` — **38/0**.

### Проверка релизного ядра (не на глаз)

Скачан файл `libkenji.so` из релиза `engine-kenji` и прочитан его заголовок:

```
ELF 64-bit LSB shared object, ARM aarch64, for Android 21, stripped
LOAD ... Align 0x4000    ← 16 КБ
NEEDED: liblog.so libdl.so libz.so libm.so libc.so
sha256 969431b3… (совпадает с EXPECTED_SHA)
```

Вывод тем же кодом, что работает в приложении:

```
релизный libkenji.so: выравнивание = 16 КБ
страницы 4 КБ  → подходит
страницы 16 КБ → подходит
```

То есть **сам файл ядра совместим и с 4-КБ, и с 16-КБ страницами**, и лишних зависимостей
(вроде .NET-рантайма) у него нет. Значит отказ, если он был, приходил не от «ядро не подходит
к телефону», а от кнопки и от загрузки в процессе — это и исправлено.

### Запасной путь: как в оригинале

Если своё ядро не готово, а официальный APK Kenji установлен, игра не уходит молча на Eden:

* на экране «Два ядра» есть кнопка «Играть через Kenji»;
* на плитке игры, поставленной на второе ядро, запуск отдаётся официальному приложению —
  с сообщением, почему (Snackbar: «Открыл игру в «Kenji»: своё ядро не готово (…)»).

## 15. Обложки, сейвы и облако

### Почему в нативной библиотеке были только буквы

`LauncherTileAdapter` **никогда не запрашивал обложку**: в `bind()` рисовалась монограмма
(буква в цветном квадрате) и всё. Загрузчик `GameIconUtils` в приложении был — им пользуется
штатный список игр и ярлыки на рабочем столе, — но нативная плитка к нему не обращалась.
Поэтому «в WebView обложки есть, а тут квадратики» было не «не грузится», а «никто не
просил».

Теперь: в плитке `ImageView` под монограммой; картинка запрашивается по той же модели `Game`
и из того же кэша Coil, что и в штатном списке. Ответ асинхронный, поэтому ячейка помечается
путём игры — обложка от прошлой строки не попадает в соседнюю. Если иконки нет (homebrew,
битый заголовок, нет ключей) — картинка прячется и остаётся буква, а не серая заглушка.

### Сейвы: что показывается и что измеряется

`SavesOverview` считает по файлам: сколько слотов, сколько весит, когда создан, когда
последнее сохранение, сколько дней не заходили, сколько времени прошло **с самого
сохранения**. Последнее — ответ на исходную жалобу «десять часов на миссии и ничего не
добился»: видно, что игра не сохранялась двенадцать часов.

Проверки: `SavesOverviewTest` — **56/0**. Отдельно закрыты случаи, на которых строки врут:
«0 дней назад» вместо «не запускалась», «только что» при отсутствии сохранений, склонение
«21 день» (в первой версии было «21 дней» — тест поймал).

### Процент прохождения: почему вручную

Настоящий процент лежит внутри сейва в формате конкретной игры, часто сжатом. Вывести его
из размера папки или числа файлов нельзя. Автоматическая «оценка» была бы выдумкой, а
выдуманный прогресс хуже отсутствующего: по нему решают, начинать ли заново. Поэтому процент
ставит человек (`ProgressMarks`, кнопки 0–100), и экран говорит это прямым текстом.

### Облако: WebDAV

Почему не Google Drive: он требует OAuth-клиента, зарегистрированного в консоли разработчика —
без него кнопка «войти» не работает ни у кого, кроме владельца проекта. WebDAV работает с
логином и паролем приложения и поддерживается Яндекс.Диском, Nextcloud, Box, Облаком Mail.ru
и домашним сервером.

| Часть | Что делает | Проверка |
|---|---|---|
| `WebDavParse` | разбор `207 Multi-Status`, сборка и кодирование путей, даты RFC 1123 | `WebDavParseTest` **37/0** |
| `WebDavClient` | PROPFIND / MKCOL / PUT / GET / DELETE, отказы словами | требует сети, на хосте не проверяется |
| `CloudSync` | слоты сейвов по профилям, заливка/скачивание по файлам, образы по кнопке | — |

Правила, заложенные в код:

* **скачивание не затирает более свежий локальный сейв** — уже стирало прогресс людям;
* **образы не заливаются автоматически** — это гигабайты и мобильный трафик;
* **`download` пишет в `.part` и переименовывает** — оборванная загрузка не оставляет
  полуфайл на месте целого;
* **отказ — фразой**, без имён исключений: «сервер не найден», «логин или пароль не подошли».

### Чего здесь нет и почему

Запуска игры «прямо из облака» нет. Эмулятору нужен локальный файл и десятки тысяч
произвольных чтений по гигабайтному образу — по сети это не «медленно», а невозможно.
Схема честная: скачать → играть → сохранения уходят обратно.

## 16. Распаковка NSZ / XCZ / NCZ: формат, а не догадка

**Жалоба:** «конвертация — ошибка, выдал ноль результата», «неправильно устроен».

**Что было не так.** Две независимые ошибки, каждая из которых делает распаковку
невозможной:

1. таблица секций читалась по смещению `+16` вместо реального `0x4000 + 8 + 8`, а число
   блоков — из `meta[12..15]`, которого в формате нет; блоки и сплошной поток после этого
   разбирались как попало;
2. шифрование секций не возвращалось: в NCZ тело секции лежит **расшифрованным**, и
   AES-128-CTR с ключом и счётчиком из таблицы должен быть применён на выходе. Без этого
   получался «правильный» поток и нерабочий NCA.

Плюс отдельно: у образов XCI корневой раздел HFS0 лежит по фиксированному смещению
**0xF000**, а код считал его как `u64` из `0x130`, умноженный на `0x200` — то есть искал
не там. Это ломало и «сохранить как NSP» для обычного XCI.

**Что сделано.** Разбор переписан по эталонной раскладке (nsz / SAK), отдельным модулем
`patch/symbiosis/ncz.cpp`:

| Часть | Правило |
|---|---|
| заголовок | 0x4000 байт копируются как есть |
| таблица | `NCZSECTN`, `u64` число секций, по 0x40 байт: смещение, размер, тип шифрования, ключ, счётчик |
| блоки | `NCZBLOCK`: версия, тип, `u8` экспонента размера, `u32` число блоков, `u64` размер, `u32[]`; блок меньше размера блока — zstd, иначе как есть |
| сплошной поток | один zstd-поток на все секции |
| шифрование | типы 3 (CTR) и 4 (BKTR) → AES-128-CTR по абсолютному смещению в NCA |
| AES | своя реализация `patch/symbiosis/aes128.cpp`: `core/crypto` из common недоступен (циклическая зависимость) |

zstd берётся из дерева Eden (`AddJsonPackage(zstd)` + `zstd::zstd` в `src/common`), свой
декодер не вендорится: рядом живёт `zstd_compression.cpp`, и второй набор символов `ZSTD_*`
сломал бы линковку.

**Проверка.** `tests/t_nsz.cpp` — 17 проверок:

| Что | Как |
|---|---|
| AES-128 | векторы FIPS-197 C.1 и B.1, CTR сверен с `openssl` |
| solid NCZ, секция BKTR | распаковка, сравнение байт в байт |
| NSZ: сжимаемая секция + несжимаемая + дырка между секциями + обычный NCA | извлечение файлов из NSP, сравнение |
| XCZ: корневой HFS0 в 0xF000, раздел secure | извлечение файлов из NSP, сравнение |
| обрезанный файл | ноль байт, понятная причина, недописанный выход удалён |

Файлы для теста собирает `tests/data/make_fixtures.py` — **отдельной реализацией того же
формата** (Python, настоящие `zstandard` и `pycryptodome`). Если бы и генератор, и
распаковщик писались по одной и той же ошибке в голове, тест подтверждал бы только
согласованность ошибки с самой собой.

`tools/run_tests.sh` требует `libzstd-dev` и без него останавливается: молчаливый пропуск
теста распаковки — ровно то, из-за чего «ноль байт» доехал до телефона.

**Чего это не проверяет.** Настоящий образ на 15 ГБ в CI не прогоняется — тест на
синтетических файлах того же формата. Поэтому первая же проверка на телефоне — на реальном
скачанном NSZ.

## 17. Дубликаты, обложки и журнал ядра

### Дубликаты игр (жалоба: «выбрал подпапку — появились дубликаты»)

Один файл приходит с разными URI, если добавить и `Games`, и `Games/Switch`:

```
…/tree/primary%3AGames/document/primary%3AGames%2FSwitch%2Fgame.nsp
…/tree/primary%3AGames%2FSwitch/document/primary%3AGames%2FSwitch%2Fgame.nsp
```

`distinctBy { it.path }` сравнивал строки целиком — они разные, поэтому появлялись две
плитки. Ключ теперь — идентификатор документа (`GameFolderList.fileKey`), то есть часть
после `/document/`. Регистр не приводится: на внутренней памяти `Game.nsp` и `game.nsp` —
разные файлы.

Проверка: `GameFolderListTest` **40/0** (было 34/0).

### Обложки (жалоба: «по-прежнему съезжают»)

Три причины, все в загрузчике:

1. **Не отменялся прошлый запрос.** Coil рисует картинку в `ImageView` сам, как только она
   готова. Запрос прошлой игры не отменялся и приходил позже нового — поверх обложки
   соседа. Проверка метки в колбэке этого не ловит: картинка уже нарисована. Теперь старый
   запрос отменяется (`GameIconUtils.inflight`), а `onViewRecycled` отменяет и очищает.
2. **Метку ставил загрузчик, а не адаптер.** При любом раннем выходе из загрузчика в
   ячейке оставалась метка прошлой игры, и запоздавший ответ считался «своим». Теперь метка
   ставится при привязке ячейки, до обращения к загрузчику.
3. **Заглушка считалась успехом.** Фетчер возвращал `default_icon` как успешный результат:
   Coil клал её в кэш по пути файла, экран показывал картинку вместо буквы, и после смены
   ключей из кэша доставалась та же заглушка. Теперь отсутствие обложки — отказ: остаётся

## 19. Ровность кадров и звук: «60 → 15 → 45 → 5» и треск в аркадах

Жалоба дословно: «звуковые эффекты и музыка с тормозами, когда анимации стабильны,
а в Zelda наоборот — звук ровный, а кадры прыгают с 60 на 15, потом на 20-45, потом на 5».

Это две разные болезни с одинаковым симптомом «лагает», и лечатся они
противоположно. Поэтому экран сначала **измеряет**, а потом советует: без чисел
«попробуйте выключить vsync» — это гадание.

### Что сделано

| Слой | Где | Что даёт |
|---|---|---|
| счётчики в движке | `patch/symbiosis/frame_metrics.{h,cpp}` | длительность каждого системного кадра (мкс), провалы аудио, сборки конвейеров; кольцо на 1024 кадра, атомики, без блокировок |
| хунки в Eden v0.2.1 | `perf_stats.cpp` `EndSystemFrame`, `sink_stream.cpp` (ветка `!queue.TryPop`), `vk_pipeline_cache.cpp` (`if (is_new)`), `oboe_sink.cpp` (`SymbiosisAudioBufferFrames`) | счётчики питаются настоящими событиями, а не таймером |
| настройка буфера звука | `settings.h` `symbiosis_audio_buffer_ms` (20 мс, 10…100) | Eden кладёт в буфер Oboe `TargetSampleCount*2` = 10 мс; на части устройств это меньше, чем задержка планировщика |
| JNI | `native_symbiosis.cpp` `frameMetrics` / `resetFrameMetrics` | снимок строкой, одна граница на всё |
| разбор снимка | `FrameMetricsText.kt` | мусор и пустой ответ не роняют экран |
| анализ | `FramePacing.kt` | доли частоты экрана, шейдерные паузы, тепловой сброс |
| экран | `PerformanceFragment` («Инструменты» → «Ровность кадров») | медиана / 90% / худшие 1% / худший кадр, причина, советы, чипы звука 10/20/30/50 мс, копирование отчёта |

### Как читаются числа

- **60 → 30 → 15** (ровно доли частоты) — упор в вертикальную синхронизацию.
  `vk_swapchain.cpp` при FIFO ждёт следующего кадра целиком: не успел на 1 мс —
  потерял 16. Такое поведение выглядит как «прыгает с 60 на 15», хотя GPU нагружен
  наполовину.
- **Медиана низкая, отдельные кадры в разы дольше** — сборка шейдера в кадре
  (`use_asynchronous_shaders=false` в v0.2.1 = сборка в потоке отрисовки).
  Лечится проходом по тому же месту и асинхронными шейдерами.
- **Ровно, потом вдвое хуже и не возвращается** — тепловой сброс частот;
  турбо-режим в этот момент делает хуже.
- **Звук при ровной картинке** — буфер 10 мс и повтор последнего кадра в
  `sink_stream.cpp`; лечится 20–30 мс, а не настройками графики.

## 20. «Распаковка закончилась без результата» и «мост упал в :kenji»

Два отчёта с устройства (itel S666LN, Android 13, 4 КБ страницы), оба — про
места, где приложение знало причину отказа и не говорило её.

### 20.1. Распаковка

Уведомление выглядело так: **«Распаковка закончилась без результата. Файлы
здесь: /storage/emulated/0/Download/Symbiosis»**. Причина в этом тексте
отсутствовала по построению: `ConverterService.finish()` выбирал текст по
одному признаку — «есть ли путь», — а путь есть всегда.

| Что было | Чем грозило |
|---|---|
| при отказе показывался путь вместо причины | «без результата» без единой подсказки, что чинить |
| формат определялся по расширению | `.zip` (и `.nsz`, переименованный из zip) уходил в нативную распаковку |
| отказ нативной части приходил как «Not an NSZ…» и схлопывался в «распаковка не удалась» | не отличить архив от битого образа |
| временный каталог брался из `std::filesystem::temp_directory_path()` | на Android `TMPDIR` не выставлен, `/tmp` нет → исключение в JNI, то есть `abort` |

Что сделано:

- `RomSniff` — определение контейнера по **первым байтам**: ZIP `50 4B 03 04`,

  (NCA/NCZ), `NRO0`. Расширение — только запасной признак, когда подпись
  переставлена. Архивы и мусор отсекаются до копирования большого файла.
- `RomTools::SetWorkDir` + `NativeSymbiosis.setRomWorkDir`: рабочий каталог
  приходит из Kotlin (кэш приложения); если он не задан — `try/catch` вокруг
  `temp_directory_path()` и запасной вариант рядом с результатом. Отсутствие
  каталога больше не «не удалось», а `No writable work directory: <путь>`.
- `ConverterReasons.outcomeText` — причина первой строкой, путь второй.
- Новые фразы причин: «это не сжатый образ», «некуда распаковать», «не удалось

### 20.2. Второе ядро

Окно «Почему не запустилось» выдавало заранее написанный текст: **«наш мост
упал в :kenji — это не «телефон не тянет». Официальный Kenji на этом
устройстве уже играет»**. Вторая половина — утверждение, которого никто не
проверял; оно отправляет человека искать проблему не там.

Процесс `:kenji` умирает от сигнала, и Android не отдаёт приложению ни номера
сигнала, ни стека — только `onServiceDisconnected`. Поэтому теперь причина
записывается **до** смерти процесса, в файл, который её переживает:

| Слой | Что пишет |
|---|---|
| `libsymbiosis_kenji.so`, обработчик `SIGSEGV/SIGBUS/SIGILL/SIGFPE/SIGABRT` | `step=…`, `crash signal=… name=… addr=… code=…`, до 12 кадров `pc=<библиотека>+0x…` |
| `debug_break(int)` в мосте | `debug_break=<код>` — ядро само сообщает об ошибке инициализации |
| метки `NoteStep` в JNI | шаг ставится перед вызовом: `dlopen`, `javaInitialize`, `deviceInitialize`, `graphicsInitialize`, `attachSurface`, `deviceLoadDescriptor`, `graphicsRendererRunLoop` |

Обработчик после записи восстанавливает `SIG_DFL` и повторяет сигнал: приложение
не глотает падение, tombstone у Android остаётся настоящим. `KenjiCrash`
разбирает файл и `KenjiCrash.verdict` разделяет два разных вывода — «падение
внутри `libkenji.so`» (чинить файл ядра) и «падение в нашей части моста».

### 20.3. Первый настоящий отчёт с устройства и что в нём было не так

Отчёт пришёл (это уже плюс: раньше на этом месте была догадка):

```
шаг: javaInitialize · сигнал: 6 (SIGABRT) · адрес: 0x2e5300005fb0
```

Что из него следует и что пришлось починить:

| Наблюдение | Причина | Что сделано |
|---|---|---|
| верхний кадр — наша же библиотека, ниже `[vdso]` | `_Unwind_Backtrace` из обработчика сигнала не проходит через сигнальный кадр: первый кадр — сам обработчик | кадры снимаются из `ucontext`: pc + цепочка x29 (frame pointer), первый кадр теперь настоящий адрес падения |
| вывод «Падение внутри libkenji.so» при кадрах из нашего .so | вердикт строился по принципу «есть ли `libkenji.so` где-нибудь в стеке» | вердикт смотрит на **верхний** кадр; добавлены отдельные выводы для «вне обеих библиотек» |
| `SIGABRT` объяснялся как обычное падение | это не сбой памяти, а `abort()` | отдельная строка про `abort()` и про то, что у .NET-ядер так заканчивается необработанное исключение |
| текста исключения нет | его печатает рантайм в журнал системы, а не в наш отчёт | после падения читается `logcat -d` (только свой UID), из него берутся строки про исключение/failfast и прикладываются к отчёту |

Сам `SIGABRT` на шаге `javaInitialize` означает: файл ядра загрузился и был
проверен по символам, но **сам код ядра остановился** при передаче ему путей и
JNI. Номер блока и текст исключения появятся в следующем отчёте — тогда и будет
видно, чинить файл или мост.

### 20.4. Распаковка: что добавилось после второго снимка

повреждены»), но не сказано, **какой файл**. Добавлено:

- имя файла в первой строке уведомления: `«Zelda.nsz»: …`;

### 26.5. Перехват JNI: что ядро спрашивает у Java

Ответ на «почему молча» получен разбором, а не догадкой: ядро не печатает
ничего, потому что умирает не от собственного исключения, а от проверки
ответа. Воспроизвести это можно только увидев вопросы.

Мост теперь передаёт ядру **свою таблицу JNI**: копию настоящей, где часть
функций заменена обёртками. Обёртка пишет вызов в `kenji-jni.txt` и передаёт
его в настоящий ART через `JavaVM::GetEnv`. Ядро получает указатель на нашу
таблицу в том же слове, где был настоящий (`JNIEnv` в C++ — структура, первое
слово которой и есть указатель на `JNINativeInterface`).

Индексы взяты из канонического `jni.h` через `offsetof` (FindClass = 6,
GetMethodID = 33, NewStringUTF = 167 …): порядок функций задан спецификацией и
одинаков у Android и OpenJDK, а имена полей — нет.

Что перехвачено: `FindClass`, `GetMethodID`, `GetStaticMethodID`, `GetFieldID`,
`GetStaticFieldID`, `NewStringUTF`, `RegisterNatives`, `ExceptionCheck`,
`ExceptionOccurred`, `ThrowNew`, `ExceptionDescribe`, `CallObjectMethod`,
`CallStaticObjectMethod`, `CallVoidMethod`, `GetObjectClass`, `NewGlobalRef`.
Вариативные вызовы переписаны на `…V`-варианты (`va_list`), чтобы не терять
аргументы.

Отказобезопасность: если `GetEnv` не отвечает или таблица не копируется, ядру
уходит настоящий `env` — перехват не может помешать запуску.

В окне падения появился раздел **«Что ядро спрашивало у Java перед
остановкой»**: только запросы имён и отметки об исключении, хвостом, потому
что важно то, что было прямо перед смертью.

### Проверка

- `tests/KenjiCrashTest.kt` — **110 проверок**: `jniLines` показывает классы,
  методы и отметку об исключении, выбрасывает `CallObjectMethod`/`NewGlobalRef`,
  берёт хвост, а не начало.
- Блок перехвата отдельно собран на хосте: `g++ -Wall -Wextra -Werror` по
  каноническому `jni.h` — ноль предупреждений.

### Чего здесь по-прежнему нет

Причина падения второго ядра на этом телефоне **ещё не установлена**: отчёт
появится только в следующей сборке, и по нему будет видно, чинить файл ядра
или мост. Утверждений вида «на этом устройстве играет» в приложении больше нет.

## 21. Быстрые настройки в игре и третий отчёт с устройства

Жалоба дословно: «в оверлее выбор настроек под каждую игру особо ничего не
меняет, их там мало, нет точного применения настроек, я их включил, но в игре
ничего не поменялось; качество поменять не могу; звуковое устройство не могу
сменить во время эмуляции».

Обе половины жалобы — про одно и то же, и обе верны.

### 21.1. Почему «ничего не поменялось»

Стандартная панель Eden умеет десять пунктов, и в ней нет ни разрешения, ни
звука. А те пункты, что есть, ядро читает в разные моменты:

| Настройка | Где читается | Вывод |
|---|---|---|
| `resolution_setup` | `VideoCore::Init` → `Settings::UpdateRescalingInfo` | только при запуске |
| `use_vsync` | `ChooseSwapPresentMode` при создании swapchain | только при запуске |
| `output_engine` | при создании звукового вывода | только при запуске |
| `symbiosis_audio_buffer_ms` | при создании звукового потока | только при запуске |
| `audio_volume` | применяется к сессиям на ходу | сразу |
| `speed_limit` | читается каждый кадр | сразу |

То есть настройки работали — но не в тот момент, когда человек ждал, и никто
ему об этом не сказал. Вывод, к которому он пришёл («настройки не работают»),
был логичным.

### 21.2. Что сделано

- `QuickPanel` — таблица «сразу / после перезапуска» с указанием, **почему** так
  (по месту в коде ядра). Под каждым пунктом панели стоит подпись, внизу —
  строка вида «Применено сразу: 1. Ждут перезапуска игры: 2.».
- В панель добавлено то, чего не было: **разрешение**, **вертикальная
  синхронизация**, **звуковой движок**, **буфер звука** (чипы 10/20/30/50 мс),
  **громкость** (ползунок, байтовая настройка `volume`).
- Кнопка **«Перезапустить игру»**: сохраняет глобальную и игровую конфигурацию,
  останавливает эмуляцию и запускает ту же игру заново. Показывается только
  тогда, когда действительно есть что применять.
- Громкость читается и пишется как `ByteSetting.AUDIO_VOLUME`: через `getInt`
  по ключу `volume` вернулся бы 0, и ползунок показывал бы тишину.

### 21.3. Третий отчёт о падении второго ядра

```
шаг: javaInitialize · сигнал: 6 (SIGABRT) · адрес: 0x2e53000005a6
кадры: libc.so+0x530f4 → libc.so+0x530c8 → libkenji.so+0x173c214
```

Кадры теперь настоящие (первый — `abort()` в libc, второй — `raise()`,
третий — код ядра). Из этого следует точный вывод, и он теперь так и
формулируется: **`abort()` вызван изнутри libkenji.so** — ядро загрузилось и
прошло проверку символов, но само остановилось при передаче ему путей и JNI.
Вердикт больше не путает «механизм» (libc) с «виновником»: libc, libm, libdl и
`[vdso]` пропускаются при выборе виновного кадра.

Что добавлено для следующего шага:

- читается **буфер крашеи** `logcat -b crash -d` — там Android хранит tombstone
  с `Abort message`, то есть текстом исключения .NET. В общем буфере его нет:
  он вытесняется за секунды, и в предыдущем отчёте поэтому были только адреса;
- строки `Abort message`, `signal 6`, `exception:` поднимаются в начало выборки.

### 21.4. «Журнал ядра» показывал 0 КБ

Файл `eden_log.txt` существовал и был пуст, а экран советовал «запустите игру» —
совет, который уже не помогал. Теперь:

- пустой файл отличается от отсутствующего: «файл создан, но пуст — свой
  файловый журнал включается отдельно от системного»;
- добавлен источник **«система»**: `logcat -d` того же приложения. Он пишется
  всегда и содержит старт ядра, отметки SymbiosisKenji и fatal-строки.

### Проверка

- `tests/QuickPanelTest.kt` — 26 проверок таблицы: что применяется сразу, что
  после перезапуска, строка состояния, подсказки по буферу, наличие объяснения
  у каждого отложенного пункта.
- `tests/KenjiCrashTest.kt` — 48 проверок, включая разбор настоящего отчёта с
  устройства: libc не обвиняется, вывод «abort() вызван изнутри libkenji.so»,
  `Abort message` попадает в выборку из журнала.
- Весь набор — **47/0**; патч целиком применяется к Eden v0.2.1

### Чего здесь по-прежнему нет

Причина `SIGABRT` в самом ядре **ещё не названа**: для этого нужен `Abort
message` из буфера крашеи, а он появится только в следующей сборке. Ни один
экран не утверждает, что ядро запустится: он говорит, на каком шаге оно
остановилось и почему это не «телефон не тянет».

## 22. Третий отчёт: битый NSZ, чужой журнал и падение с открытой панелью

Три жалобы из одного сообщения, и у каждой своя причина — ни одна не была
«файл плохой» или «телефон не тянет».

### 22.1. Твёрдый NSZ объявлялся повреждённым — виноват zstd, не файл

Файл «Vault of Power [01004F302847E000][v0] (0.31 GB).nsz» отвергался с
сообщением о повреждённых сжатых данных. Формат тут не при чём: наш разбор
NCZ (`patch/symbiosis/ncz.cpp`) соответствует описанию контейнера —
заголовок, секции по 0x40 байт, блоки `NCZBLOCK` по 24 байта и таблица
размеров. Ошибку выдал сам декодер, `ZSTD_getErrorName` даёт ровно
«Data corruption detected».

Причина — пин zstd. В Eden v0.2.1 `cpmfile.json` держит zstd на `b8d6101fba`
(1.5), а в этой версии включена оптимизация ветвления в
`ZSTD_decodeSequence`, которая на ARM64 считает неверно и портит данные.
Upstream Eden исправил это сменой пина на `33618c8` — версию с отменённой
оптимизацией (коммит «Support block-compressed NSZ and XCZ»).

Что сделано:

- `tools/apply_patch.sh` поднимает пин в `cpmfile.json` до `33618c8` и
  проверяет результат: без этого шага `grep '"33618c8"'` валит сборку, потому
  что иначе любой правильный NSZ снова будет «битым»;
- в `docs/GUIDE.md` §16 добавлен абзац: сообщение о повреждении больше не
  означает «скачайте заново», и что делать, если оно всё-таки появилось.

Поля задаются в форме, которую понимает `CPMUtil` именно v0.2.1. В master
Eden достаточно `version` + `hash` (там `version` сама служит ссылкой на
коммит), а `CPMUtil` v0.2.1 ищет `TAG`, `SHA` или `BRANCH`: на голый
`version` он пишет «REPO defined but no TAG, SHA, BRANCH, or URL» и уходит на
master zstd, где скачивание падает. Это и случилось в прогоне `41327290304` —
сборка легла на `zstd-populate`. Поэтому `sha` задаётся явно, и хеш
проверен не на слово: sha512 архива `github.com/facebook/zstd/archive/33618c8.tar.gz`
совпадает с `2b006c3c…`.

Проверено: на свежем клоне v0.2.1 `PATCH_APPLIED files=190`, блок `zstd` в
`cpmfile.json` — `sha 33618c8`, `version 33618c8`, `min_version 1.5`, хеш
`2b006c3c…`; этот же блок отдельно прогнан на копии исходного файла.

### 22.2. Журнал в отчёте был от другого процесса

В отчёте стояли строки PID 4628, а процесс к тому моменту имел 24319:
`logcat -d -t 400` без фильтра отдаёт хвост общего буфера, куда попадают
записи уже закрытых процессов того же приложения. Такой журнал не просто
бесполезен — он указывает не на ту причину.

- `KenjiCrash.logcatArgs(pid, buffer, lines)` — аргументы с `--pid`;
- `KenjiCrash.filterByPid(text, pid)` — повторная фильтрация по колонке PID
  (строки без даты, то есть продолжения многострочных сообщений, наследуют
  решение предыдущей записи);
- служба живёт в `:kenji`, поэтому `Process.myPid()` — это PID упавшего ядра;
- если журнала своего процесса нет, отчёт говорит это прямо, а не молчит.

### 22.3. Текст исключения .NET — из файла, а не из журнала

В отчёте о сигнале есть адреса, но нет текста. Теперь `ArmStdioCapture()` в
мосте перенаправляет stdout и stderr процесса `:kenji` в
`kenji-stdout.txt` рядом с отчётом, без буферизации (процесс умирает до
`fflush`). `KenjiCrash.exceptionLines` достаёт оттуда строки про исключение и
кадры стека, и они идут в отчёте первым блоком — «Что сказало ядро перед
остановкой».

### 22.4. Падение при открытой панели быстрых настроек

Причина в самом устройстве панели: на каждое изменение вызывался
`addQuickSettings()`, то есть `removeAllViews()`, — из обработчика того
элемента, который в этот момент удалялся с экрана (у радиокнопки из её
`setOnCheckedChangeListener`, у чипа буфера из `onClick`). Плюс каждый цвет
брался через `MaterialColors.getColor`, который бросает исключение, если
атрибута нет в теме.

- панель не пересобирается: `quickPanelRefresh` обновляет тексты, подсветку
  чипов и видимость кнопки перезапуска;
- кнопка «Перезапустить игру» создаётся всегда и только показывается;
- цвета берутся через `quickColor(...)` — по порядку атрибутов, с запасным
  оттенком вместо исключения;
- всё тело панели под `try/catch`: ошибка в одном пункте пишется в журнал и
  показывается строкой, а не закрывает игру;
- `UiGuard` ставит обработчик необработанных исключений в
  `EmulationActivity.onCreate` и пишет их в `symbiosis/ui-crash.txt`
  (`KenjiCrash.describeThrowable` — время, поток, тип, стек). Нативный сбой
  ядра идёт мимо него, своим отчётом.

### Проверка

- `tests/KenjiCrashTest.kt` — **70 проверок, 0 падений**: к ним добавились
  разбор stderr-файла (исключение, внутренняя причина, кадры, отброс шапки),
  фильтр по PID (чужая строка отброшена, продолжение своей — оставлено) и
  формат записи необработанного исключения.
- C++ мост: `ArmStdioCapture` и `InstallCrashHandlers` проверены на хосте
  настоящим `SIGSEGV` — файл stderr создан, строка `Unhandled exception.`
  в нём, в отчёте есть `step=` и кадры `pc=`.
- Весь набор хоста — **11/0, skipped=12**; патч на свежем v0.2.1 —
  `PATCH_APPLIED files=190`; `check_kotlin_refs` — 104 файла, 0 проблем;
  `check_jni_names` — 76, 0 проблем; `check_string_refs` — 1484 строки.

### Чего здесь по-прежнему нет

Распаковка после смены пина **на устройстве ещё не проверена** — вывод «файл
теперь читается» будет только после прогона с тем же NSZ. Причина `SIGABRT`
внутри ядра тоже не названа: теперь для неё есть текст из stderr, но он
появится в следующем отчёте, а не задним числом.

## 23. Четвёртый отчёт: «Block 306 unpacked to 409600 instead of 1048576»

### 23.1. Вчерашнее объяснение про zstd было неверным — и это видно из отчёта

В §22.1 причиной называлась версия zstd в сборке. Новый отчёт показал другое:
ядро ответило `Block 306 unpacked to 409600 bytes instead of 1048576`, и это
**наша** фраза из `ncz.cpp`, а не ошибка zstd. `ZSTD_decompress` блок
распаковал успешно — просто получилось 400 КиБ вместо 1 МиБ, и наша проверка
«ровно размер блока» отвергла годный файл.

Проверка была неверной по смыслу: размер блока — это сколько места блок
занимает в потоке, а не сколько в нём данных. Судить должен итог.

Что сделано:

- блок короче своего места **принимается**; ошибкой остаётся только блок
  длиннее места (это уже сдвиг таблицы, а не короткий хвост);
- добавлен независимый судья — размер NCA из заголовка (смещение `0x08`). Он
  не зависит от того, как прочитана таблица секций: если распакованное
  кончается ровно на этом байте, файл целый;
- если поток кончился, а размер не сошёлся, отказ называет всё: где кончился
  поток, сколько обещала таблица, что говорит заголовок NCA, сколько блоков
  прочитано и сколько из них было короче своего места;
- заявленный в `NCZBLOCK` размер теперь может быть **меньше** суммы секций
  (чужие компрессоры так пишут); ошибкой остаётся только «больше».

### 23.2. Попутно найденная потеря данных

`BlockPump::Next` при исчерпании блоков возвращал `false`, уже скопировав часть
байт в буфер вызывающего. Эти байты терялись: последние 400 КиБ файла просто
не попадали в результат, без ошибки. Теперь при исчерпании возвращается
частичное заполнение, а «блоков нет» сообщается следующим вызовом.

Тест `tests/t_nsz.cpp` получил два случая:

- `short.ncz` — последний блок короче своего места, размер в заголовке NCA
  верный: распаковка обязана пройти, длина файла — ровно размер NCA;
- `short_bad.ncz` — то же, но заголовок NCA врёт про размер: отказ, в тексте
  есть `ended at`, недописанный файл удалён.

### 23.3. «Что сказало ядро» было пусто — потому что журнал просили не в том формате

`logcat` вызывался с `-v brief`, а фильтр по PID разбирал колонки формата
`threadtime` (метка времени, PID, TID). В `brief` этих колонок нет, поэтому
фильтр выбрасывал **все** строки, включая свои, и в отчёт попадало «строки
своего PID система не отдала». Плюс сам `--pid` на телефоне не сработал: флаг
не приняли, ошибка ушла в тот же поток и была отфильтрована.

- `logcatArgs()` больше не передаёт `--pid` и просит `-v threadtime`;

## 24. Пятый отчёт: «вылазит ошибка» при настройках и «ядро молчит»

### 24.1. «Перезапустить игру» отправляло в лаунчер — обход штатной смены игры

В `restartGameWithSettings` стояло три вызова: `NativeLibrary.stopEmulation()`,
`activity.finish()`, `EmulationActivity.launch(...)`. Каждый по отдельности
выглядит логично, вместе — ломает ровно тот путь, который Eden уже написал.

`EmulationActivity` объявлен `singleTop`. Новый intent на него попадает в
`onNewIntent` → `handleSwapIntent`, который **сам** останавливает сессию
(`stopForRomSwap`), **дожидается** остановки потока эмуляции
(`notifyWhenEmulationThreadStops`) и только потом запускает игру заново.
Наши три вызова этот механизм обходили:

- `finish()` закрывал активити, а запуск из закрывающейся активити Android
  выбрасывает — человек оставался в лаунчере (это и есть «отправило в лаунчер»);
- `stopEmulation()` в обход фрагмента оставлял поверхность и поток в
  состоянии, из которого следующий кадр ронял процесс («вылезла ошибка»).

Теперь: сохранить настройки, закрыть меню, попросить тот же экран
перезапуститься. Всё остальное делает Eden.

### 24.2. Панель: одно место для применения настройки

Каждый пункт сам звал `saveGlobalConfig`/`savePerGameConfig`, и падение на
любом из них выглядело одинаково. Появился `applySetting(label) { … }`:
пишет метку шага в нативный отчёт, ловит исключение, пишет причину в журнал,
показывает её строкой — и только потом сохраняет конфиг. Настройка, которая не
применилась, больше не забирает с собой игру.

### 24.3. Причина падения теперь видна на экране

`UiGuard` писал файл, но файл никто не показывал. Добавлено:

- нативный обработчик для ОСНОВНОГО процесса (`armMainCrashLog` в
  `native_symbiosis.cpp`): SIGSEGV/SIGABRT внутри `libyuzu-android.so` не
  доходит до Java, а раньше именно так и падала эмуляция;
- метка шага (`setMainStep`): в отчёте теперь есть строка вида
  «настройки: громкость» или «перезапуск игры»;
- диалог «Прошлый запуск остановился» при входе в игру: сигнал или тип
  ошибки, шаг, до четырёх кадров, кнопка «Скопировать». Файл после показа
  переименовывается в `ui-crash-last.txt`, чтобы одна причина не показывалась
  каждый раз.

Обработчик проверен на хосте настоящим `SIGSEGV` — код для проверки берётся
из самого `native_symbiosis.cpp`, а не из копии: в файле появляются
`crash signal=11 name=SIGSEGV … step=приложение` и шесть кадров `pc=`.

### 24.4. Почему журнал ядра был пуст: PID был не тот

`crashMessage` собирается в ОСНОВНОМ процессе (служба `:kenji` к этому моменту
мертва), а фильтр журнала брал `Process.myPid()` — то есть номер лаунчера.
Отсюда «строки своего PID 8674 система не отдала»: 8674 — это лаунчер, а падал
другой процесс. Теперь служба записывает свой PID в `kenji/kenji-pid.txt`
**до** первого касания ядра, и отчёт фильтрует журнал по нему.

### 24.5. Почему «ядро ничего не написало»

Файл `kenji-stdout.txt` был создан и пуст — и это правда: .NET на Android
перенаправляет `Console`/stderr в **logd**, а не в файловые дескрипторы. Значит
искать текст исключения надо в журнале, с меткой `DOTNET`. Метка добавлена в
приоритеты `fatalLines`, а формулировка в отчёте больше не утверждает, что
ядро промолчало.

## 25. Шестой отчёт: NSP распаковался, ядро его не приняло

Две строки из отчёта с устройства, и обе — про одно и то же: проверка говорила
меньше, чем знала.

### 25.1. «Ядро не принимает этот файл» после успешной распаковки

Файл `Vault of Power … (0.31 GB).nsz` распаковался (журнал: `NCZ unpacked:
306 MiB, 3 section(s)`, результат 307 МиБ), а шторка ответила безымянным
отказом. Текст в `Converter.probeFile` — запасной: он появлялся, когда
`NativeSymbiosis.romProblem` возвращал пусто.

Причина расхождения найдена в самом Eden:

- `getIsValid` (`game_metadata.cpp:239`) для NSP и XCI зовёт
  `Loader::IsBootableGameContainer`, а тот через `HasApplicationProgramContent`
  требует внутри контейнера NCA с парой `{Application, Program}`;
- `diagnoseRom` проверял только `ReadProgramId`, который читает номер игры и
  на структуру не смотрит.

Файл, у которого целое оглавление, но нет такого NCA (или он не разобрался),
проходил вторую проверку и падал на первой — без единого слова. Теперь
`diagnoseRom` после успешного `ReadProgramId` повторяет проверку ядра и, если
она не прошла, называет звено: `not_bootable|<причина>`.

Причина считается в `RomTools::DescribeContainer` — без ключей, только по
оглавлению PFS0:

| Что найдено | Что написано человеку |
|---|---|
| нет файла `*.cnmt.nca` | ядро узнаёт игру только по нему |
| файл `.nca` без метки `NCA3` по смещению 0x200 | это ошибка распаковки, а не ключей |
| всё на месте | причина в содержимом, чаще всего нет title key в `prod.keys` |

Найдено и исправлено по дороге: `EndsWithInsensitive` умеет ровно четыре
символа расширения, поэтому `.cnmt.nca` не распознавался никогда — первая
версия `DescribeContainer` на исправном контейнере отвечала «CNMT нет». Это
хорошо видно в тесте `t_rom`: тот же файл до правки и после даёт разные ответы.

### 25.2. Ядро падает на `javaInitialize`, а текста нет

Факты из отчёта: `core loaded and verified`, затем процесс умирает молча;
SIGABRT, кадры `libc.so+0x530f4 → libc.so+0x530c8 → libkenji.so+0x173c214`.
Строк `DOTNET` в журнале нет вовсе.

Разбор адреса: `addr=0x2e5300005a55` — это не адрес памяти. Для сигнала,
посланного через `tgkill`, поле `si_addr` накладывается на `si_pid`/`si_uid`;
`0x5a55` = 23125, а это PID самого ядра, `0x2e53` — uid приложения. Значит
`abort()` вызвал сам процесс, изнутри `libkenji.so`, а не система и не OOM.
`libkenji.so` — NativeAOT (экспорт `DotNetRuntimeDebugHeader`), и перед abort()
он печатает причину в stderr — то есть в `kenji-stdout.txt`, который у нас уже
перенаправлен.

Прошлая запись в §24.5 («.NET пишет в logd») была догадкой и не подтвердилась:
строк нет ни в журнале, ни в отборе. Отсюда правки:

- `KenjiCrash.consoleLines` — если отбор по знакомым словам ничего не нашёл,
  показываются последние строки файла как есть. Молчание теперь возможно
  только для пустого файла, и оно так и называется;
- в отбор добавлены формулировки NativeAOT: `Process terminated.`,
  `Fatal error.`, `Invalid Program:`, `Assertion`;
- `SysExit` читает `ApplicationExitInfo` для процесса `:kenji` (Android 11+):
  причина от системы и tombstone, где есть строка `Abort message:` — текст, с
  которым процесс остановил себя сам, и кадры с именами функций. Снимок
  сохраняется как `kenji-exit.txt`;
- если у журнала процесса нет знакомых строк, показывается его хвост без
  отбора — раньше этот случай заканчивался словами «журнала система не дала».

### Проверка

- `tests/KenjiCrashTest.kt` — **101 проверка**: `consoleLines` не теряет текст

## 26. Седьмой отчёт: ложный вердикт, адрес abort и молчание ядра

Три факта из отчёта 17:10-17:12, и все три — про одно: проверка говорила с
уверенностью, которой не имела.

### 26.1. «Файл не похож на NCA» — ошибка проверки, а не распаковки

В шторке появился список из семи файлов, у всех «0 МиБ», и вердикт «файл …
не похож на NCA: по смещению 0x200 стоит …». Список и размеры уже полезны —
видно `.tik`, `.cert`, `.cnmt.nca`, три `.nca`. А вердикт неверен:

Eden **не** сверяет метку `NCA3` с открытыми байтами по 0x200. Он читает
заголовок через `AesXtsStorage` и лишь потом зовёт `CheckNcaMagic`
(`src/core/file_sys/fssystem/fssystem_nca_reader.cpp:66-90`). По 0x200 лежат
байты подписи. Значит проверка обвиняла любую распаковку, включая исправную —
включая эту. Это ровно тот случай, когда новая диагностика вреднее старой.

Что теперь:

- метка по 0x200 не проверяется вовсе;
- «распаковка записала пустоту» говорится только если файл короче 0x204 байт —
  это единственное, что видно без ключей;
- размеры печатаются с одним знаком после запятой, а не целыми мебибайтами:
  «0 МиБ» у сертификата и у NCA в 900 КиБ выглядели как «не записалось ничего»;
- список больше не обрезается на «и ещё N»: именно за обрезкой на устройстве
  спрятался файл, на который жаловалась проверка;
- полный разбор пишется в `почему-не-открывается.txt` рядом с результатом.

### 26.2. Что за файл не разобрался — теперь отвечает ядро

`HasApplicationProgramContent` пуст не потому, что «не так собран контейнер»,
а потому, что NCA не разобрался: `ReadNCAs` кладёт NCA в карту только при
успешном статусе. Поэтому `diagnoseRom` теперь строит `FileSys::NSP` сам
(`OpenContainerAsNsp` есть только внутри `loader.cpp`, в анонимном namespace)
и перечисляет каждый NCA с его типом и статусом из `GetResultStatusString`:
`MissingTitlekey`, `IncorrectTitlekeyOrTitlekek` и так далее.

Заодно это объясняет, почему в контейнере есть `.tik`, а игра всё равно не
открывается: тикет сам зашифрован titlekek, и без него ключ из тикета не
извлечь. Так что «положите prod.keys с title keys» — не отговорка, а точное
действие.

### 26.3. Кадр `libkenji.so+0x173c214` — это возврат после `bl abort`

Разобрано по таблице PLT: `0x362b690` → слот `0x3632620` → `abort` (сверено с
`.rela.plt` и `.dynsym`). По этому адресу стоит `sub sp, sp, #0xc0` — пролог, а
сам вызов лежит на два байта раньше, в хвосте предыдущей функции:

```
0173c200: bl   #0x362b670   ; strcmp
0173c204: stp  x29, x30, [sp, #-0x10]!
0173c208: mov  x29, sp
0173c20c: bl   #0x173d6c4   ; mov w0,#6; … ; → общая точка остановки
0173c210: bl   #0x362b690   ; abort
0173c214: sub  sp, sp, #0xc0
```

`0x173d6c4` — это `mov w0, #6; mov x1, xzr; mov x2, xzr; b …` — та самая общая
функция остановки с кодом 6. Ничего не печатает ни один из них: сообщения
здесь нет по построению, поэтому искать текст в журнале было бессмысленно.

Смысл: в ядре есть тихие пути к `abort()` (17 мест вызова), и один из них
сработал. Виновника называет только кадр выше по стеку — а цепочка x29 на нём
и обрывалась, потому что libc своих кадров frame pointer не ведёт.

### 26.4. Что добавлено в отчёт, чтобы виновника назвать

- второй проход по стеку: слова вверх от `sp`, похожие на адреса возврата в
  загруженный код (проверка через `dladdr`, только свои библиотеки и `libc`);
  помечаются тем же `pc=`, поэтому видны в окне рядом с кадрами FP;
- регистры аргументов `x0…x3, x29` отдельной строкой `regs` — по ним видно, с
  чем именно ядро не справилось (указатель на строку, дескриптор, код);
- `SysExit`: для `REASON_SIGNALED` текст больше не говорит «убит извне» — тот
  же код даёт `abort()` внутри процесса.

## 27. Раунд 5. Ядро: перехват `abort()`, частота звука, ключи при каждом запуске

### 27.1. Что на самом деле нарисовал отчёт `libkenji.so+0x173c214`

Кадр разобран по самому файлу ядра (57 321 040 Б, `.text` начинается с
`0x16ca650`, поэтому смещение совпадает с адресом в файле):

```
0x173c1d8: ldr x8, [x21, #0x28]      ; канарейка стека, проверка
0x173c1e4: b.ne 0x173c200            ; не совпала — путь отказа
0x173c200: bl __stack_chk_fail@plt
0x173c204: stp x29, x30, [sp, #-0x10]!  ; ← отдельная крошечная функция
0x173c20c: bl 0x173d6c4              ; печать через log_error (приоритет 6)
0x173c210: bl abort@plt              ; ← отсюда и адрес возврата 0x173c214
```

Вывод: `0x173c214` — возврат из `abort@plt` внутри служебной функции, которую
вызывают **18 мест** ядра (`0x16fed10`, `0x16fef3c`, `0x1703100`, `0x1703838`,
`0x170388c`, `0x17038a8`, `0x1703a74`, `0x1703b64`, …). Сама функция ничего не
сообщает: печатать ей нечего, поэтому в журнале текста и не было. Виновник —
всегда кадр **выше** неё, и именно его в отчёте не было.

`abort` в ядре — импортируемый символ (`abort@plt` → `0x362b690`), поэтому его
можно перехватить на нормальном стеке, до входа в libc.

### 27.2. Перехват `abort()`

- экспортируется обёртка `abort` (`visibility("default")`, `noreturn`);
- вызывающий и цепочка x29 пишутся ДО входа в libc:
  `abort-caller=libkenji.so+0x…`, `abort-pc=…` (до 12 кадров);
- чтобы ядро действительно нашло нашу обёртку, библиотека перед `dlopen`
  ядра поднимается в глобальную область символов (`PromoteToGlobalScope`),
  результат проверяется сравнением `dlsym(RTLD_DEFAULT,"abort")` с адресом
  обёртки и пишется в отчёт строкой `abort interposer: активен/не активен`;
- если поднять не удалось — всё работает как раньше, ядро получает обычный
  `abort`, отчёт просто не получит новых строк.

### 27.3. Частота дискретизации

Устройство жалуется на хрип в музыке с вокалом; переключатели варианта и
буфера не помогали. Причина, которую это объясняет: Eden открывал поток с
`setSampleRate(TargetSampleRate)` (48 кГц) и `OpenSLES`, а на телефоне,
который живёт на 44,1 кГц, драйвер обязан пересчитывать каждый кадр.

- новая настройка `symbiosis_audio_rate`, по умолчанию **0 — «как решит
  драйвер»**: `0` доходит до Oboe как «частота не задана»;
- `48000` и `44100` остаются для ручного выбора;
- кадры буфера считаются от той частоты, с которой поток реально откроется
  (`SymbiosisEffectiveRate()`), иначе «30 мс» на 44,1 кГц были 24 мс;
- замеры (`symbiosis/audio_metrics.*`) снимаются с открытого потока:
  запрошенная и фактическая частота, каналы, буфер в кадрах и **в
  миллисекундах**, ёмкость, порция, `getXRunCount`, число вызовов, драйвер.

### 27.4. Ключи: не только `prod.keys` и `title.keys`

закрытый, и сборка 41505907208 упала на этом

## 28. Раунд 6. Перехват по имени не сработал — правка слота в таблице переходов

### 28.1. Что показал отчёт с устройства (21:04)

Отчёт пришёл **от предыдущей сборки**: строка `• верхние кадры:` есть только в
`a1dac4c`, а в текущей она называется `• кадры:`. Поэтому отсутствие
`abort-caller=` в нём ничего не говорит о перехватчике — в той сборке его не
было вовсе.

Но одно стало ясно: полагаться на порядок загрузки нельзя. Символ `abort`
находится в глобальной области только если наша библиотека попала туда до
того, как ядро привязало свои импорты. На телефоне это условие может не
выполниться, и тогда перехват молчит, а отчёт неотличим от отчёта без
перехватчика.

### 28.2. Что добавлено

- `symbiosis/got_patch.*` — правка записи `R_*_JUMP_SLOT` для `abort` в
  `.rela.plt` уже загруженной библиотеки ядра: адрес слота ищется по
  `dl_iterate_phdr`, страница со слотом открывается на запись и закрывается
  обратно в `READ|WRITE`;
- вызывается сразу после `dlopen` ядра и до первого вызова в него
  (`ArmAbortTrap`), поэтому не зависит ни от области видимости, ни от порядка;
- в отчёт пишутся две строки состояния: `abort interposer: активен/не активен`
  и `got patch: abort — подменено слотов: N` (или причина отказа);
- окно отчёта показывает эти строки (`• перехват abort: …`), а если перехват не
  взведён, вердикт говорит это прямо, вместо рассуждений о кадрах.

### 28.3. Проверка

- `tests/t_got.cpp` — **9 проверок** на настоящей библиотеке, собранной самим
  тестом: слот `abort` находится, подменяется ровно один, вызов уходит в
  подмену, отсутствующее имя возвращает причину, пустые аргументы и чужая
  библиотека не роняют процесс.
- Найдено и исправлено по дороге: после подмены страница слота оставалась
  `PROT_READ`, и процесс падал уже после успешной подмены (на хосте — код
  выхода −1). Теперь возвращается `READ|WRITE`.
- `tests/KenjiCrashTest.kt` — **125 проверок**: состояние перехвата

- Весь набор хоста — **59/0, skipped=3**.

## 29. Раунд 7. SIGSEGV в самом мосте: bionic не дописывает базу в .dynamic

### 29.1. Что было в отчёте (03.11 00:19, сборка 92888aa)

Первый отчёт **новой** сборки — с ней наконец видно и цепочку, и состояние
перехвата (`abort interposer: активен`). Падение переехало: шаг `dlopen`,
SIGSEGV по адресу `0x47330`, верхний кадр `libsymbiosis_kenji.so+0x2ebf4`.

### 29.2. Как найдено

Артефакт сборки 92888aa скачан целиком, из APK вынут
`lib/arm64-v8a/libsymbiosis_kenji.so`, и смещения сопоставлены с его же
`dynsym`:

```
0x2ebf4 -> Symbiosis::PatchImport+0x300
0x2b27c -> Java_..._KenjiBridge_nativeLoad+0x43c
0x2a920 -> abort+0x0
```

Дизассемблер по точке падения:

```
0x2ebec: cmp  w25, #0
0x2ebf0: csel x8, x28, x26, ne
0x2ebf4: ldr  x8, [x8, #8]     ; SIGSEGV, адрес 0x47330
```

`x8 = 0x47328` — это `DT_JMPREL` **как он лежит в `.dynamic`**, то есть
смещение. Код брал его за абсолютный адрес.

### 29.3. Почему не поймали на хосте

Тест на хосте шёл под glibc, а glibc **дописывает базу загрузки в `.dynamic`**:
значение там уже абсолютное, поэтому проверка «слот находится и подменяется»
проходила. bionic (Android) этого не делает — оставляет смещение. Одинаковый
код, разное поведение загрузчика.

### 29.4. Что изменено

- `Symbiosis::ImageAddress()`: адрес из `.dynamic` принимается, только если он
  попадает в образ библиотеки (области `PT_LOAD`); иначе пробуется
  `base + значение`; иначе — отказ **с причиной**, а не падение;
- так же проверяются индекс символа, смещение имени и адрес самого слота;
- в отчёт при отказе: `got patch: abort — таблицы .dynamic вне образа
  библиотеки` / `… слот перехода вне образа библиотеки`.

### 29.5. Проверка

- `tests/t_got.cpp` — **15 проверок**: абсолютный адрес (glibc) и смещение
  (bionic) дают один результат, значение вне образа отвергается, нулевая база и
  пустой список областей не ломают разбор; плюс настоящая подмена `abort` в
  собранной тестом библиотеке;
- в APK этой сборки есть обе новые строки отказа (проверено по скачанному
  артефакту), в предыдущей их нет;
- весь набор хоста — **59/0, skipped=3** (`t_got` 15/0, `t_audio` 23/0).

## 30. Причина отказа ядра: собственный журнал ядра вместо догадок

Сборка `adb5da5` → запуск `41630704196` **SUCCESS**,
APK: https://gofile.io/d/Mk8HFph8, MD5 `a9d95cfa4698dcc0af2894c705643bf2`.

### 30.1. Что показал прошлый отчёт

`init-args: path=…/files/kenji exists=1 dir=1`,
`loader tap: dlopen ok, dlsym ok`, `init-callback: original=-1 calls=1` —
и **ни одной строки `dlreq`**. Ядро при инициализации загрузчик не зовёт,
значит ненайденной внешней функции нет, и причина отказа лежит внутри.

### 30.2. Что говорит исходник ядра

`src/LibKenjinx/Android/JniExportedMethods.cs`:

```csharp
public unsafe static bool JniInitialize(nint jpathId, nint jniEnv)
{
    string? path = Marshal.PtrToStringAnsi(jpathId);
    bool init = Initialize(path);          // ← отказ рождается здесь
    Interop.Initialize(new JEnvRef(jniEnv));
    Interop.Test();
    return init;
}
```

`Initialize` ловит **любое** исключение и печатает его `Console.WriteLine(ex)`,
то есть в stdout процесса, а не в отчёт. Единственное, что он делает до
первого падения, — заводит каталоги данных и **открывает свой журнал**:

```csharp
AppDataManager.Initialize(basePath);      // Directory.CreateDirectory(Logs, Games, Profiles, Keys)
ConfigurationState.Initialize();
LoggerModule.Initialize();
FileStream logFile = FileLogTarget.PrepareLogFile(logDir);   // может вернуть null
Logger.AddTarget(new AsyncLogTargetWrapper(new FileLogTarget("file", logFile), …));
```

`PrepareLogFile` при любой неудаче (нет каталога, нельзя создать файл)
возвращает **null**, и `new FileLogTarget("file", null)` валится на
`StreamWriter(null)`. Отсюда отказ без единой строки: журнала ещё нет, а
причина именно в нём.

### 30.3. Что изменено

- `KenjiBridge.ensureCoreDirs()` — каталоги `Logs`, `Games`, `Profiles`, `Keys`
  создаются **до** запуска ядра, результат каждого проверяется;
- `KenjiBridge.coreLogFile()` / `canWriteCoreLog()` — самый свежий
  `Ryujinx_*.log` и пробная запись в каталог;
- отчёт (экран «Ядро не запустилось») печатает **дословно** последние 12 строк
  журнала ядра, а если журнала нет — говорит, создан ли каталог и работает ли
  в нём запись, и какие каталоги создать не удалось;
- `tools/check_kotlin_syntax.py` — разбор скобок и вложенных комментариев
  (эта же ошибка — `Logs/*.log` внутри комментария — уже стоила одного прогона:
  компилятор назвал чужой файл и чужую строку). Проверка включена в сборку.

### 30.4. Проверка фактами

- сборка `41630704196` — **SUCCESS**;

## 32. Отказ инициализации — это проверки окружения рантайма

Сборка `b935f83` → запуск `41804876254` **SUCCESS**,
APK: https://gofile.io/d/QviqaVlj, MD5 `a5c2195f33088979acc78d307b9bde13`.

### 32.1. Что пришло с устройства

```
init-callback=-1 calls=1 [libkenji.so+0x16fe4d4]
передано ядру: path=…/files/kenji exists=1 dir=1 env=0x7bcc37c688
сигнал 11, адрес 0x0
кадры: libkenji.so+0x174a09c → libkenji.so+0x1a70140 → libsymbiosis_kenji.so+0x2c790
Собственного журнала ядра нет: каталог Logs есть, запись в него работает.
Под ярлыком RyujinxLog система тоже ничего не сохранила.
```

То есть: путь верный, каталоги создаются, запись работает, файла журнала
нет — ядро остановилось **до** первой строки своего лога. Значит причина
родилась ещё раньше первого `Logger.AddTarget`.

### 32.2. Что показывает файл ядра

`javaInitialize` = `0x1a6fe00`. Её первый же вызов — `0x17062cc` →
`0x170611c` → обработчик из `[база+0x4091290]`, то есть `0x16fe4d4`
(наша обёртка и вызывала его: `init-callback-fn=libkenji.so+0x16fe4d4`).
Внутри:

```
0x16fe4d4: mov w0,#1 ; bl 0x1704320 ; tbz w0,#0 → return -1
0x1704320: bl 0x173c2d8 ; tbz w0,#0 → return 0
0x173c2d8: bl 0x1740774 ; возврат 0 → return 0
           bl 0x173d6e4 ; возврат 0 → return 0
           bl 0x173db04 ; возврат 0 → return 0
```

`0x173db04` — проверка окружения рантайма. Дословно:

```
page  = sysconf(40)                          ; 4096 — размер страницы
cpus  = sysconf(96)                          ; -1 или число процессоров
sdk   = atoi(__system_property_get("ro.build.version.sdk"))
        syscall(283, 0, 0)                   ; membarrier, только запрос
p     = mmap(NULL, page, RW, PRIVATE|ANON, -1, 0)
        if (mlock(p, page) != 0) return 0    ; ← ненулевой ответ = ОТКАЗ
        if (pthread_mutex_init(&lock, NULL)) return 0
```

`0x1740774` ставит обработчики `sigaction(11)` и `sigaction(8)`.
`0x173d6e4` читает переменные окружения диагностики (`DbgEnableMiniDump`,
`DbgMiniDumpName`, `CreateDumpLogToFile`, `DbgMiniDumpType`) и `statfs("/sys/fs/cgroup")`.

Любой нулевой ответ отсюда → `init-callback=-1` **без единой строки в логе**.
Рантайм остаётся неинициализированным, managed-куча не заводится — и первая
же аллокация в `javaInitialize+0x33c` падает в bump-аллокаторе по адресу 0
(`0x174a09c: str x0,[x12]`, `x12 = [bump] = 0`). Это ровно кадры из отчёта:
`0x174a09c → 0x1a70140`.

### 32.3. Что добавлено

- **`pal:`** — мост повторяет те же вызовы и пишет ответы: страницы (`40` и
  `_SC_PAGESIZE`), процессоры (`96`), `mmap`, `mlock` с `errno`,
  `pthread_mutex_init`, `membarrier`. `sysconf(96) == -1` сам по себе —
  отказ, поэтому он в отчёте отдельным числом.
- **`call:`** — настоящие вызовы самого ядра (`sigaction`, `mmap`, `sysconf`,
  `pthread_mutex_init`) с аргументами и ответами. По последней строке видно,
  на чём ядро остановилось — это и есть названная причина.
- **`mlock` в ядре подменён**: отказ блокировки страницы не означает «ядро не
  работает», а настоящий `errno` пишется в отчёт, чтобы подмена не была
  молчаливой.

### 32.4. Проверка

- сборка `41804876254` — **SUCCESS**, набор хоста `59/0 skipped=3`;
- `KenjiCrashTest` — **160/0** (было 154): разбор `pal:`, отказ `mlock`,

## 34. Причина найдена: .NET-GC резервирует 256 ГиБ, а их негде взять

Сборка `4d5389a` → запуск `41811697339` **SUCCESS**,
APK: https://gofile.io/d/RN1wwCdP, MD5 `8307756a87d2221845a3fdf65b00e5ec`.

### 34.1. Строка, которая всё объяснила

Отчёт с устройства (04.11 12:49, сборка `6d3eb99`) дал последнюю строку
перехвата вызовов:

```
→ mmap(274877911040) = FAIL errno=12
```

`274877911040 = 256 ГиБ + 4096` (`0x4000001000`), `errno=12` — `ENOMEM`.

Это не наша проверка и не выделение под данные: столько **.NET-GC**
резервирует себе под «регионы» кучи при инициализации. По документации
Microsoft: на 64-битной системе по умолчанию резервируется 256 ГБ
виртуального адресного пространства, а на ARM64 под Android его 39 бит —
512 ГиБ на весь процесс, вместе с ART, загруженными библиотеками и стеком.

### 34.2. Цепочка целиком

1. `Initialize()` → первый разбор JSON в `ConfigurationState.Initialize()`
   инициализирует GC;
2. GC резервирует 256 ГиБ → `mmap` отвечает `ENOMEM`;
3. исключение ловится `catch (Exception ex)` → `Console.WriteLine` → `false`;
4. в отчёте `init-callback=-1`;
5. наш обход возвращает 0, ядро продолжает как ни в чём не бывало, но
   рантайм не инициализирован — и первая же аллокация в `javaInitialize+0x33c`
   падает в bump-аллокаторе по нулевому адресу (`0x174a09c → 0x1a70140`).

То есть **файл ядра не повреждён и мост не виноват**: не хватает настройки
среды для GC.

### 34.3. Что сделано

- мост задаёт `DOTNET_GCRegionRange=400000000` (16 ГиБ, голый hex) **до
  `dlopen`** — NativeAOT заводит рантайм в инициализаторе модуля;
- в этом файле ядра строка `DOTNET_GCRegionRange` присутствует, то есть
  настройка поддерживается;
- форма `0x…` NativeAOT молча игнорирует (известная особенность), поэтому
  приставка отрезается, если значение задано вручную;
- отчёт печатает `gc: DOTNET_GCRegionRange=…` и **итог**: «не понадобилась»,
  «резерв кучи 16.0 ГиБ — настройка прочитана» или «всё равно просило
  256.0 ГиБ — настройка не прочитана»;
- перехват `mmap` печатает размеры по-человечески («256.0 ГиБ») и, если
  резерв не прошёл по `ENOMEM`, называет причину словами.

### 34.4. Проверка

- сборка `41811697339` — SUCCESS;
- `KenjiCrashTest` — **168/0**; в dex и мосте этой сборки есть все новые
  строки (`DOTNET_GCRegionRange`, `400000000`, «настройка прочитана»,
  «настройка не прочитана», «не хватило адресного пространства»).

## 35. Ядро инициализировалось. Дальше — криптография .NET

Сборка `a8446f4` → запуск `41815485762` **SUCCESS**,
APK: https://gofile.io/d/tTJpINM6, MD5 `797924a565dfdb30bc35e174e0d67434`.

### 35.1. Что пришло с устройства (13:35)

```
init-callback: original=0 calls=1
00:00:00.087 |N| Application Initialize: Using base path: …/files/kenji
00:00:00.090 |E| .NET TP Worker No usable version of libssl was found
SIGABRT, кадры: libc +0x530f4 → libsymbiosis_kenji.so+0x2bbd4 → libkenji.so+0x17b0874 → …
```

`init-callback=0` — **инициализация ядра прошла**: настройка кучи (§34)
сработала, журнал ядра появился, каталог данных принят. Через 3 мс рабочий
поток .NET сказал, что нет `libssl`, и процесс остановился.

### 35.2. Почему

Криптография .NET (`System.Security.Cryptography`) ищет OpenSSL по списку
имён. В файле ядра это видно строками: `libssl.so.3`, `libssl.so.1.1`,
`libssl.so.1.0.2`, `libssl.so.1.0.0`, `libssl.so.10`, `libssl.so`, и рядом
сообщение `No usable version of libssl was found`. Не найдя ни одного, она
**останавливает процесс** — это её штатное поведение, а не сбой ядра.
В Android своих `libssl`/`libcrypto` нет, Eden их не носил, а оригинальное
приложение Kenji кладёт обе рядом с собой.

### 35.3. Что сделано

- `patch/libs/arm64-v8a/libssl.so` (507 408 Б) и `libcrypto.so` (2 367 064 Б) —
  OpenSSL 1.1.1l для Android arm64 из дерева Kenji-NX; `SONAME libssl.so`,
  зависимость `libcrypto.so` по имени;
- `apply_patch.sh` кладёт их в `jniLibs/arm64-v8a`, AGP упаковывает в
  `lib/arm64-v8a` (сборка с `useLegacyPackaging` — библиотеки распаковываются
  при установке, `dlopen` находит их по имени);
- мост загружает обе **до** ядра: сначала по своему каталогу (абсолютный
  путь), затем по имени; результат — строкой `ssl: libssl.so=ok (путь)` либо
  `ssl: libssl.so=HET (причина)` с пояснением, что процесс будет остановлен.

### 35.4. Проверка

### 36.1. Что пришло с устройства (14:02)

```
init-callback: 0 calls=1
→ mmap(17179873280 = 16.0 ГиБ) = ok        ← настройка кучи сработала

… |N| Application .ctor: System Firmware not installed
сигнал 11, кадры: libart.so+0x309ee8 → … → javaInitialize+1292
```

Ядро прошло инициализацию, создало `SwitchDevice`, дошло до
`Interop.Initialize(...)` и упало **внутри ART**.

### 36.2. Почему — наша ошибка

Кадр `javaInitialize+0x1292` → `Interop.Initialize` → `JniHelper.GetVirtualMachine`
→ `GetJavaVM` в ART. Разбор по адресу:

```
0x1a93274: ldr x1, [x19]        ; x19 = наш JNIEnv, x1 = таблица функций
0x1a9327c: ldr x1, [x1, #0x6d8] ; GetJavaVM из таблицы
…
0x1a932ac: blr x3                ; вызов через делегат → в ART
```

Вызов уходит в ART с указателем `env = &g_tapEnv` — **нашей поддельной
структурой**, у которой первое слово указывает на копию таблицы функций.
ART же получает не таблицу, а сам указатель и через него находит поток:
`Thread::ForEnv(reinterpret_cast<JNIEnvExt*>(env))` читает поля, лежащие
сразу **за** указателем на таблицу. У нашей структуры этих полей нет —
читался мусор, отсюда SIGSEGV глубоко внутри libart.

Перехват JNI (`InstallJniTap`) был написан в ранних раундах, когда ядро
умирало раньше, чем доходило до JNI. Теперь, когда инициализация проходит,
он и стал причиной.

### 36.3. Что изменено

- ядру отдаётся **настоящий** `JNIEnv`; обёртки `Tap_*`, таблица-двойник и
  `InstallJniTap` удалены;
- вместо них `PrepareJni`: до вызова ядра находим

  кэширует (`test`, `updateUiHandler`, `frameEnded`, `updateProgress`,
  `getSurfacePtr`, `getWindowHandle`), и пишем результат в `kenji-jni.txt`.
  Ненайденное и исключения называются до падения, а не после;
- в предзагрузку добавлены `libicuuc.so` и `libicui18n.so`: 64 ненайденных
  `dlsym` (`u_strlen_50` …) — это пробы версий ICU, без него .NET не умеет
  работать со строками;
- формулировка отчёта честная: «Что мы проверили в Java за ядро».

## 37. Почему игра закрывалась чёрным экраном

Сборка `d6af3ad` довела ядро до старта: «проверка ядра» отвечает
«ядро запущено». Но запуск игры заканчивался чёрным экраном и возвратом в
лаунчер без единого слова. Причин две, обе в нашем коде.

### 37.1. Порядок вызовов был перепутан

Официальный Kenji делает так (`MainViewModel.kt`):

```
graphicsInitialize → graphicsInitializeRenderer → deviceInitialize
  → deviceLoadDescriptor
```

У нас было `deviceInitialize` → `graphicsInitialize` → рендерер (в
`attachSurface`). Ядро первым делом проверяет `Renderer == null` в своём
`InitializeContext` и возвращает `false`, то есть **без рендерера устройства
не существует**. Дальше `deviceLoadDescriptor` видит
`EmulationContext == null` и отдаёт отказ. Игра не могла открыться вообще.

Второе требование того же файла: `deviceInitialize` вызывается **из главного
потока** («We are only able to initialize the emulation context on the main
thread») — у нас он шёл из рабочего.

Исправлено: `preparePlay` теперь только поднимает ядро и настраивает графику,
`attachSurface` создаёт рендерер, `deviceInit` создаёт устройство — и уже
из UI-потока, с ожиданием результата.

### 37.2. В APK не было `libopenal.so`

`deviceInitialize` начинается с `new OpenALHardwareDeviceDriver()`, а его
конструктор зовёт `alcOpenDevice` — P/Invoke в `libopenal.so`. В Android такой
библиотеки нет, и в нашем APK её не было: в списке библиотек лежали только
ядра, OpenSSL и мосты. Вызов происходит внутри `[UnmanagedCallersOnly]`-метода,
исключение оттуда не перехватывается, .NET завершает процесс — ровно чёрный
экран и вылет.

Официальное приложение собирает openal-soft из подмодуля
(`src/KenjinxAndroid/app/src/main/cpp/libraries/openal`, форк
`git.ryujinx.app/kenji-nx/openal-soft`) и кладёт `libopenal.so` рядом с ядром.
Теперь его собирает CI тем же CMake и тем же NDK 28.2, что и остальной натив,
и `tools/apply_patch.sh` копирует его в `jniLibs/arm64-v8a/`. В форке есть
`-Wl,-z,max-page-size=16384`, то есть выравнивание страниц 16 КБ — как у ядра.

### 37.3. Отчёт, который не теряется

Падение плеера до сих пор не оставляло ничего: отчёт включала только
«проверка ядра», а игра запускается отдельным процессом и умирает молча.
Теперь `KenjiPlayerActivity` до первого касания ядра пишет PID и включает
отчёт, отмечает шаги `1/6 … 6/6`, а `onDestroy` ставит метку «вышли штатно».
Метки нет — процесс умер. `KenjiReport` собирает причину в основном процессе
(`crashMessage`: шаг, сигнал, кадры, stdout ядра, его собственный журнал) и
показывает её при возврате в список игр кнопкой «Скопировать».

Названный отказ (`fail`) теперь тоже не считается штатным выходом: причина
живёт не шесть секунд на чёрном экране, а в отчёте.

### 37.4. Прошивка — словами ядра

Без прошивки коммерческая игра не запустится, и до сих пор это было не
отличить от поломки. `nativeFirmwareVersion` спрашивает у ядра
`deviceGetInstalledFirmwareVersion` и пишет в отчёт строку
`fw: <версия>` или `fw: прошивка не установлена`; та же строка видна в
статусе плеера.

## 39. Игра запускается, но кадров нет: прошивка второго ядра

Сборка `12faa3e` дошла до «второе ядро · играет» — устройство создалось,
игра передана ядру, ввод поднялся, цикл идёт. Дальше чёрный экран и тишина.

### 39.1. Где ядро ищет прошивку

По исходникам Kenji:

| Что | Где лежит у Eden | Где ищет второе ядро |
|---|---|---|
| ключи | `<данные>/keys/prod.keys` | `<данные ядра>/system/prod.keys` |
| прошивка | `<данные>/nand/system/Contents/registered/*.nca` | `<данные ядра>/bis/system/Contents/registered/*.nca` |
| игры | папки игр | `<данные ядра>/Games` |
| профили | — | `<данные ядра>/Profiles` |
| журнал | — | `<данные ядра>/Logs` |

Раскладка внутри одна и та же, разнятся только корни: у Kenji
`DefaultNandDir = "bis"`, у Eden перед `system` стоит `nand`.

не поднимается — ровно чёрный экран без ошибки.

размер) лежит в `.firmware-source`, совпал — копирования нет. Ссылки не
годятся: на `/storage/emulated` (FUSE) нет ни символьных, ни жёстких.

Перенос идёт ДО `javaInitialize`: `ContentManager` перечисляет прошивку в
момент инициализации и добавленное позже не увидит. Результат — в отчёте
строкой `прошивка: …`, а версия, которую называет само ядро, — в статусе
игрока (`прошивка: 17.0.0` вместо `не установлена`).

### 39.3. Вместо чёрного экрана — счётчик

Плеер теперь раз в три секунды пишет в строку статуса: сколько секунд идёт

## 40. «Как в Kenji»: папка данных вместо переноса прошивки

Замечание по делу: в Kenji ничего не «импортируется». Ядру передаётся ОДНА
папка (`javaInitialize(path)`), и внутри неё оно само заводит своё дерево.
Если прошивка там уже лежит — она находится на месте, копировать нечего.

Проверено по исходникам: `AppDataManager.SetupBasePaths` создаёт в
переданной папке `Games`, `Profiles`, `system` (ключи), а
`VirtualFileSystem.SystemNandPath = BaseDir/bis/system` — прошивка. У нас же
папка была жёстко приватной (`Android/data/<пакет>/files/kenji`), и другого
способа отдать ядру прошивку, кроме копирования из Eden, не оставалось.

### 40.1. Что сделано

- папку данных второго ядра можно выбрать: `KenjiBridge.setDataDir`, пункт
  «Папка данных второго ядра» на экране «Ядра»;
- в диалоге — поле пути и **найденные на телефоне** папки, в которых уже есть
  прошивка ядра (`KenjiData.candidates`, обход в фоне, глубина 2, не больше
  400 каталогов, чтобы не поймать ANR); у каждой — что внутри
  (`KenjiData.describe`: прошивка, ключи, игры, запись);
- `seedFirmware` первым делом проверяет `bis/system/Contents/registered` в
  выбранной папке: файлы есть → «прошивка уже в папке ядра: N файлов —
  переноса нет», копирования не происходит вообще;
- если прошивки нет ни в папке, ни в Eden — в статусе игрока теперь прямо
  написано «прошивки нет — укажите папку с прошивкой в „Ядра“» вместо

### 40.2. Чего нельзя, и это не наша выдумка

`Android/data/<чужой пакет>/files` (там официальный Kenji держит свои данные,
`AppPath = getExternalFilesDir(null)`) приложению недоступен даже с
`MANAGE_EXTERNAL_STORAGE` — это ограничение Android 11+, а не наша лень.
Поэтому кандидаты ищутся только там, куда доступ есть; если у человека
прошивка лежит в такой папке, её надо один раз положить в доступное место
(например `/sdcard/Kenji/bis/system/Contents/registered`) — и выбрать его.

## 43. Исключение в гостевом потоке: разбор и что сделано

### 43.1. Что было в отчёте с телефона (04.11, 20:04, PID 28267)

```
00:00:15.538 |E| {Common} Kernel ThreadStart: Unhandled exception in guest thread:
System.Reflection.TargetInvocationException ---> System.NullReferenceException
  at IAccountServiceForApplication.IsUserAccountSwitchLocked(ServiceCtx)+0x3c
  → DynamicInvokeInfo.InvokeWithFewArguments → InstanceMethodInvoker.Invoke
  → RuntimeMethodInfo.Invoke → IpcService.CallCmifMethod+0x600
  → ServerBase.Process+0x674 → ServerBase.ServerLoop+0x6f0 → KThread.ThreadStart+0xac
```

Java-методы найдены все (FindClass ok, шесть `GetStaticMethodID` ok), то есть
мост ни при чём: исключение пришло изнутри ядра, в его собственном потоке.

### 43.2. Откуда берётся пустая ссылка

По исходнику ядра (`libryujinx_bionic`):

```csharp
// IAccountServiceForApplication
public ResultCode IsUserAccountSwitchLocked(ServiceCtx context)
{
    return context.Device.Processes.GetProcess(context.ClientProcessId)
        .ApplicationControlProperties.UserAccountSwitchLock;
}
```

- `Processes.GetProcess(pid)` — не «найти во что бы то ни стало»: при промахе он
  печатает предупреждение и возвращает `ActiveApplication`, а тот **равен `null`**,
  если ни один процесс ещё не стартовал (`_latestPid == 0`);
- значит исключение означает одно из двух: процесса игры ещё нет
  (`LoadApplication` не отметился) или он есть, но `ApplicationControlProperties`
  пусты. Второе в коде не встречается — `ProcessResult` заполняет их в
  конструкторе всегда. Остаётся первое: **игра попросила сервис раньше, чем
  ядро зарегистрировало её процесс**.

Это и объясняет «чёрный экран без кадров»: исключение убивает гостевой поток,
`frameEnded` не вызывается ни разу, цикл отрисовки стоит.

### 43.3. Что поправлено в запуске

Профиль — единственное, что в этом вызове зависит от данных, а не от гонки:

1. **`KenjiBridge.seedProfile`** копирует профиль Eden (`profiles/*.json`) в
   `<папка ядра>/Profiles` при первом запуске, если там пусто. Раскладка у двух
   ядер одна, файлы переносятся как есть. При пустом профиле ядро само заводит
   «KenPlayer», но это поведение конкретной сборки, а не гарантия.
2. **`nativeOpenedUser`** (новый JNI-экспорт `userGetOpenedUser`) — ядро само
   называет открытого пользователя. Строка пишется в наблюдение
   (`kenji/play-watch.txt`) и в отчёт о падении; если пусто, в окне плеера
   появляется предупреждение «профиль не открыт — сервис учётной записи может
   упасть».
3. **`KenjiCrash.guestFailure`** переводит стек на человеческий: «Игра
   остановилась на вызове сервиса эмулятора «IAccountServiceForApplication»:
   ядро не смогло ответить на обычный запрос и вернуло пустоту. Это внутренняя
   ошибка самого ядра…». Строка попадает в блок «Что это значит» отчёта, а не
   в лог.

Запуск при пустом профиле **не блокируется**: подозрение — не доказательство,
и запрещать игру из-за него нельзя.

## 44. Падение 04.11 22:12:49 — наша ошибка типа в мосту (найдено, исправлено)

### 44.1. Что было на самом деле

Игра **загрузилась**: в журнале ядра

```
00:00:03.113 |I| Loader Start: Application Loaded: Teenage Mutant Ninja Turtles: Shredder's Revenge v1.0.9 [0100fe701475a000]
00:00:03.113 |I| Loader Start: Process identity: Application pid=109 program=0100fe701475a000 …
```

и все пять вызовов пина рендерера прошли (`deviceSetSurfaceRotation`,
`graphicsRendererSetSize 720x1532`, `graphicsSetFullscreenStretch(True)`,
`deviceRecreateSwapchain`, `graphicsSetPresentEnabled(True)`).
Умер процесс уже **после** них, в Kotlin:

```
I ExceptionHandle: at org.yuzu.yuzu_emu.utils.KenjiBridge.rendererKick(KenjiBridge.kt:685)
I ExceptionHandle: at org.yuzu.yuzu_emu.activities.KenjiPlayerActivity.surfaceCreated$lambda$19(KenjiPlayerActivity.kt:232)
```

Строка 232 — это `val kick = KenjiBridge.rendererKick(w, h, displayRotation())`,
строка 685 — `return if (err.isEmpty()) …`.

Причина: в C++ функция была объявлена `JNIEXPORT void JNICALL`, а в Kotlin —
`external fun nativeRendererKick(...): String`. JNI связывает функции по имени
и **не сверяет тип возврата**. Kotlin получил в регистре возврата `null`,
объявил его как `String` и упал с `NullPointerException` на `err.isEmpty()`.
Это ошибка, добавленная в раунде 20 вместе с самим пином.

Отсюда же и «отчёта о падении нет»: обычное исключение Java до нативного
обработчика сигналов не доходит, процесс завершает система.

### 44.2. Исправлено

1. `nativeRendererKick` возвращает `jstring`: пустая строка — все пять вызовов
   сделаны, иначе «ядро не знает: <символы>». Молча пропустить символ нельзя —
   «пинок сделан» и «пинок не сделан» должны отличаться.
2. `KenjiBridge.rendererKick` читает ответ как **nullable** и трактует пустое
   как успех: даже при будущем расхождении типов это не падение.
3. `tools/check_jni_names.py` теперь сверяет **типы возврата** (Kotlin ↔ C++):
   `String↔jstring`, `Int↔jint`, `Unit↔void` и т. д. На первом запуске он и
   нашёл расхождение: `TYPE MISMATCH: KenjiBridge.nativeRendererKick — Kotlin
   String, C++ void`. Этот шаг уже есть в CI, то есть такой класс ошибок
   больше не проходит сборку.
4. Поток запуска плеера обёрнут в `try/catch`: любая будущая ошибка в нашем
   коде даёт строку «внутренняя ошибка плеера: …» на экране и в отчёте, а не
   «Приложение остановлено».
5. `UiGuard` ставится и в плеере (раньше — только в Eden): необработанное
   исключение Java пишется в `symbiosis/ui-crash.txt`, а `KenjiProbeService`
   включает этот файл в отчёт блоком «Необработанная ошибка Java в процессе
   ядра». Раньше причина уходила вместе с процессом.
6. Формулировка отчёта «так бывает при нехватке памяти» убрана как
   необоснованная: в этом случае причина была совсем другой.

Прошлый вывод («ядро не нашло процесс игры») уточняется. По исходнику:


## 47. Почему игра снова ушла на Kenji, хотя была «переведена на Eden»

### 47.1. Что произошло

14:22 игра упала, отчёт сказал «переведена на Eden: выбор сохранён».
17:36 игра снова пошла на Kenji и снова упала тем же исключением.

Разбор кода дал **три независимые дыры**, и любая из них даёт такой результат:

1. **Явный выбор перезаписывал автоматику, и никто об этом не говорил.**
   Долгое нажатие → «Запустить на Kenji-NX» вызывает `runOnCore`, а тот
   пишет `setCoreFor(KENJI)`. Пометка Eden затиралась молча. Если человек
   просто проверял, починилось ли, — он снова получал падение и не знал,
   что сам отменил перевод.
2. **Запись делалась через `apply()`** — асинхронно. Приложение как раз в
   этот момент показывает отчёт о падении; если процесс закрывают, запись
   может не дойти, а сообщение «сохранено» уже напечатано.
3. **Записка удалялась сразу после попытки.** Даже если выбор не сохранился,
   второго шанса не оставалось: файл `core-fallback.txt` стирался.

Плюс: ключ игры считался от **полного пути** (SHA-256). Одна и та же игра,
открытая другим способом (папка через внешнее хранилище, «недавние»), давала
другой ключ — и перевод не находился.

### 47.2. Что исправлено

1. **Записка решает запуск, а не настройка.** `launchOn` перед стартом Kenji
   спрашивает `CoreFallback.isMarked`: если за игрой есть записка — игра идёт
   на Eden, с сообщением и причиной. Записка переживает перезапуски.
2. **Записка исчезает только по двум причинам:** игра успешно пошла на Eden
   (или человек сам выбрал Eden), либо человек **явно** выбрал Kenji. Во
   втором случае приложение говорит прямо: «Запускаю на Kenji-NX по вашему
   выбору. Прошлый запуск эта игра уронила…». Диалог долгого нажатия тоже
   показывает записку и предупреждает, что выбор Kenji её сотрёт.
3. **Запись выбора проверяется.** `setCoreFor` пишет через `commit()` и
   возвращает результат; `CoreFallback.applyIfAny` читает выбор обратно и
   говорит правду: «переведена и проверено» / «сохранить не удалось, записка
   оставлена» / «путь не сохраняется — выберите Eden вручную».
4. **Второй ключ — по имени файла.** `EngineStore` пишет выбор под двумя
   ключами (полный путь и имя файла) и читает второй, если точного нет.
   Одинаковый файл, открытый другим путём, теперь узнаётся.

ниже — «ключей игр нет: ни одной строки «0100… = 32hex»». Одно из двух было
неправдой, и это был разбор.

Причины, каждая проверена тестом:

- **разделитель**: файлы в природе встречаются с `:`, с табуляцией и с
  пробелами вокруг `=`; разбор понимал только `=`;
- **кодировка**: `title.keys` бывает в UTF-16 и с BOM — прочитанный как UTF-8,
  он выглядит пустым, потому что между буквами стоят нули;
- **отписка вместо ответа**: «ни одной строки» печаталось и тогда, когда
  строки были, просто не подходили.

Теперь `TitleKeys.decode` разбирает UTF-16LE/BE и BOM, `parts()` терпим к
разделителю и невидимым знакам, а отчёт печатает `survey`: сколько строк с
разделителем, сколько принято (с ролью — игра/обновление/дополнение) и по
каждой отвергнутой — причину. Значение ключа в отчёт не попадает: только левая
часть и длина правой.

Установка файла («Установить title.keys») теперь приводит строки к
`id = key`, отбрасывает `FFFF…` и говорит, что именно не подошло, если не
подошло ничего.

### 53.2. «Один файл — много игр»

Сказано прямо, и это правка текста, а не кода: `prod.keys` — ключи консоли,
нужные всем играм сразу; `title.keys` — ключи игр, и **один такой файл
содержит ключи многих игр и подходит ко всем им сразу**. Так и написано в
отчёте («один файл покрывает все эти игры сразу») и в руководстве отдельным
пунктом.

### 53.3. Папка второго ядра указывала на прошивку

В отчёте: `папка данных: …/Eden/bis/system/Contents/registered`. Это не корень
данных, а папка прошивки: ядро завело бы дерево внутри дерева, а ссылка на
прошивку Eden ушла бы не туда.

строка «прошивка: ссылка на …» либо «копия, N файлов».

### 53.4. Снова «собран неверно» на живом файле

## 56. «Раз есть билет — ключ внутри?» Да, у обычного

### 56.1. Что в билете на самом деле

Человек прислал `prod.keys` (12 619 Б, 204 ключа). В нём **есть
`titlekek_00…titlekek_20`** (21 штука) и `master_key_*`. Это значит, что ключ
из обычного (common) билета можно расшифровать прямо на телефоне.

Разметка (Nintendo Switch Brew, Ticket): подпись, затем данные 0x2C0:
`+0x40` блок ключа 0x100, `+0x141` тип ключа (0 — обычный, 1 — под консоль),
`+0x145` ревизия мастер-ключа, `+0x160` Rights ID. Старый код читал Rights ID
по жёсткому смещению 0x2A0 и не трогал блок ключа вовсе — отсюда «билет без
права» на всём подряд.

### 56.2. Новое: `TicketKey`

- `parse` — находит данные по типу подписи (0x140 для RSA-2048, 0x240 для
  RSA-4096), читает тип, ревизию, блок ключа и Rights ID;
- `derive` — берёт `titlekek_XX` (или выводит из `titlekek_source` +
  `master_key_XX`, как hactool) и расшифровывает ключ игры AES-128-ECB;
- `refusal` — честная причина, когда нельзя: персонализированный билет,
  права FF, нет `titlekek_XX`;
- `readProdKeys` — читает только нужные строки `prod.keys`.

`NspProbe` теперь читает **билет целиком** (потолок 0x800) и отдаёт его в
`Result.ticket`. Обход `GameHelper` при отсутствии ключа сам достаёт его из
билета и **дописывает в `title.keys`**, затем просит ядро перечитать ключи.
В диалоге плитки то же самое делается по нажатию (`GameHelper.ticketKeyFor`).

Мусор отсеивается: AES не проверяет данные, поэтому нулевой или однородный
результат за ключ не выдаётся.

### 56.3. Простыня в диалоге — убрана

`native_symbiosis.cpp` склеивал пять разных причин подряд («нет NCA… вероятно
обновление или DLC… каждый NCA по отдельности… дополнительные файлы ключей…
положите prod.keys»). Теперь берётся первый NCA с отказом и называется его
состояние и наличие ключа; остальное не перечисляется. То же — в
`NspProbe.verdict`: одна причина на ответ.

### 56.4. Ввод ключа

Если идентификатор подставлен и ключ пуст — сообщение «идентификатор игры
верный, осталось вставить ключ: 32 hex-символа», а диалог **не закрывается**,
чтобы вставленное не терялось.

## 57. Ключ достаётся сам — по всем файлам игры

### 57.1. «Не имею понятия, как достать ключ с телефона»

Так и должно быть: знать про `.tik` и `titlekek` человек не обязан. Приложение
мобильное — оно само проходит по своим файлам.

- `GameHelper.harvestTicketKeys()` — проходит **по всем** файлам библиотеки
  (и открывающимся, и нет), собирает билеты, группирует по идентификатору игры
  и берёт ключ из **любого рабочего**: у одного и того же тайтла бывает и
  сжатый, и распакованный файл, и билет мог уцелеть только в одном.
- найденные ключи дописываются в `title.keys`, ядро перечитывает их;
- по каждой игре без ключа в отчёт идёт причина: «билета внутри нет»,
  «персонализированный», «права FF», «нет titlekek_XX».
- запуск: **сам** при входе на экран «Ключи и прошивка» (в фоне) и кнопкой
  «Достать ключи из файлов игры»; результат виден в отчёте.
- `probeContainer` теперь открывает и `content://`, и обычный путь к файлу —
  раньше второй вариант молча не читался, а именно так путь и приходит из
  библиотеки в некоторых случаях.

### 57.2. Что будет, если ключа нет ни в одном билете

Тогда его нет и в файлах: у «персонализированного» билета ключ заперт под
консоль, у билета с правами FF прав нет вовсе. Это не лечится на телефоне, и
приложение говорит это одной строкой, а не «попробуйте ещё раз».
