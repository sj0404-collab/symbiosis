## 12. Плагины: правки без пересборки

Плагин — это правила, а не код, поэтому его можно проверить целиком на хосте: от текста
файла до «какие настройки уедут в ядро и какая пометка появится на плитке».

```bash
kotlinc tests/PluginEngineTest.kt \
  patch/android/utils/{PluginJson,PluginApi,PluginEngine,BuiltinPlugins,EngineHybrid,
                       NativeLibraryPresenter,LibraryIndex}.kt \
  -include-runtime -d pe.jar && java -jar pe.jar
```

```
passed=93 failed=0
```

Что держат эти 93 проверки:

```
ok   лишняя запятая названа словами
ok   повтор поля — ошибка
ok   слишком большая вложенность
ok   новая схема не принимается           [schema 99]
ok   опечатка в настройке названа с подсказкой  [«memy» → список допустимых]
ok   недопустимое значение настройки        [memory=999]
ok   ядро проверяется по имени              [«kenij»]
ok   массив — любое из                      [ext: [nsz, xci]]
ok   число меньше — не срабатывает на 8
ok   порядок списка не влияет
ok   при равном приоритете решает id
ok   одинаковые сообщения не дублируются
ok   важное наверху
ok   конфликт ядер замечен, победитель назван
ok   мусор в патче игнорируется
ok   действие на плитке не подменено
ok   пометка не повторяется дважды
ok   встроенный набор разбирается и применяется
ok   шаблон не срабатывает никогда
```

Три решения, которые эти проверки защищают:

1. **Массив значений — «любое из», а не «и».** Самая частая ошибка в таких форматах:
   `"ext": ["nsz","xci"]` не может означать «и nsz, и xci» — условие стало бы невыполнимым.
2. **Опечатка — ошибка загрузки.** Имя настройки сверяется с `EngineHybrid.FIELDS`, значение —
   со списком допустимых. «Плагин молча ничего не делает» хуже, чем «плагин не загрузился,
   вот причина».
3. **Порядок применения задан, а не случайно сложился.** Приоритет, затем id; при равном
   приоритете результат одинаков на любом устройстве. Конфликт не запрещён (общий набор +
   личный хотфикс — законная комбинация), но назван словами.

### Проверено в собранном APK

Run 41204815335, `24005c0f110e942353c3ef8608286033`, https://gofile.io/d/o1TY0dRF

```

ok   PluginEngine in dex
ok   PluginStore in dex
ok   string plugins_title is in the resource table
ok   string plugins_description is in the resource table
```

### Чего здесь нет и почему

Плагины **не могут исполнять код**: нет загрузки dex, нет shell, нет сети. Это ограничение, а
не недоделка — загружаемый код означал бы, что любой файл из чата получает права приложения.
Правил хватает на исходную задачу: плохо работающая игра почти всегда лечится настройкой,
ядром или честной пометкой «этот файл не откроется».

## 13. Папки, конвертер и след выхода

### Список папок: почему он терялся

Механизм был в коде, а не в «глюках». В `GameHelper.getGames()` стояло:

```kotlin
if (badDirs.isNotEmpty()) { ... gameDirs.removeAt(it - offset) ... }
NativeConfig.setGameDirs(gameDirs.toTypedArray())
```

Папка, у которой не подтвердилось разрешение, **удалялась из настроек и
записывалась укороченным списком**. Разрешение отзывается не только руками: система снимает
его сама после падения процесса. Дальше — ровно то, что видел пользователь: падение при
выходе из игры, следующий запуск, «осталась одна папка из четырёх». Вернуть остальные нельзя
было даже вручную: путь уже нигде не записан.

Плюс рядом стояло схлопывание «слоёв»: если `Games` и `Games/Switch` в списке, родитель
удалялся, и игры из его корня пропадали.

Что теперь:

| Было | Стало |
|---|---|
| нет доступа → папка удаляется | папка остаётся, помечается «нет доступа», нажатие возвращает доступ |
| родитель съедается вложенной папкой | обе остаются; дубликаты отсекаются по пути |
| список живёт только в конфиге ядра | вторая копия в prefs, пишется `commit()`, возвращает пропавшие |
| добавить папку — только в расширенной панели | кнопка «Добавить папку» на экране папок |
| убрать папку — только очисткой данных | долгое нажатие → «Убрать из списка» (с подтверждением) |

Проверки: `GameFolderListTest` — **34/0**, включая «одна битая строка зеркала не убивает
остальные» и «мелкий обход родителя не отменяет обход вложенной папки».

### Конвертер: почему не было ни уведомления, ни прогресса

Очередь распаковки жила в обычном `Thread` внутри процесса и складывала результат в
`files/converter` — приватную папку, невидимую ни одному файловому менеджеру. Уведомления не
было не потому, что забыли: его не могло быть, работа не была объявлена системе. Уход с
экрана → система прибивает процесс → распаковка обрывается на середине.

Теперь `ConverterService` — foreground-служба (`specialUse`, без лишних разрешений):
уведомление с текущим файлом, счётчиком и кнопкой «Остановить»; результат в
`Download/Symbiosis`; путь написан и в уведомлении, и в приложении; разрешение на
уведомления спрашивается в момент первой распаковки (без него на Android 13+ уведомление
не показывается вообще).

### Панель «видела не все игры»

Панель читала только кэш из настроек, нативный лаунчер — живой список. Два разных ответа на
вопрос «сколько у меня игр». Теперь порядок один: живой список, кэш — только если обхода
ещё не было.

### Краш при выходе

Причину не выдумываю: без журнала её не видно. Добавлен след — метки «запуск игры»,
«остановка эмуляции», «эмуляция остановлена», и отчёт в «Инструменты» → «Диагностика»:
время, шаги, и завершилась ли прошлая сессия сбоем (`previousSessionCrashed`). По этому
тексту видно, падает ли ядро внутри остановки или уже на возврате в библиотеку.

Само последствие сбоя — потерю папок — я убрал отдельно, и оно больше не зависит от того,
что именно упало.

## 14. Кнопка «Скачать ядро» и совместимость

### Почему кнопка не срабатывала

Три причины в одном месте, все — в `EnginesFragment`:

```kotlin
if (busy) return
busy = true
...
busy = false            // ← не выполнится, если корутину отменили
```

1. **Флаг залипал.** Скачивание идёт в `viewLifecycleOwner.lifecycleScope`. Уйти с экрана —
   корутина отменяется на `withContext`, строка `busy = false` не исполняется, и все
   следующие нажатия молча игнорируются до пересоздания экрана. Теперь `finally`.
2. **Плашка была не видна.** Прогресс и ошибки добавлялись в конец `root`, то есть ниже
   видимой части прокрутки. Нажатие «ничего не делало» — хотя сообщение было. Теперь плашка
   вставляется нулевой позицией, рядом с кнопкой.
3. **Кнопки могло не быть вовсе.** Она создавалась только при `EngineLoader.deviceSupported()`.
   Если проверка не проходила, карточка оставалась без действий и без объяснения. Теперь
   кнопка есть всегда: либо «Скачать (55 МБ)», либо «Скачать нельзя» и рядом — причина.

### Совместимость: что проверяется и чем это доказано

`DeviceCompat` проверяет три вещи и называет их по отдельности:

| Проверка | Плохо, если | Что говорит пользователю |
|---|---|---|
| архитектура | нет `arm64-v8a` | «процессор не arm64» + совет про официальный APK |
| разрядность процесса | `Process.is64Bit() == false` | «приложение работает 32-битным процессом» |
| страницы памяти vs ELF | 16 КБ страницы и `p_align < 16 КБ` | «ядро собрано под страницы 4 КБ» |

Разбор ELF и таблицы `auxv`/`AT_PAGESZ` — обычные функции над `ByteArray`, поэтому на них
есть тесты с синтетическими заголовками: `DeviceCompatTest` — **38/0**.

### Проверка релизного ядра (не на глаз)

Скачан файл `libkenji.so` из релиза `engine-kenji` и прочитан его заголовок:

```
ELF 64-bit LSB shared object, ARM aarch64, for Android 21, stripped
LOAD ... Align 0x4000    ← 16 КБ
NEEDED: liblog.so libdl.so libz.so libm.so libc.so
sha256 969431b3… (совпадает с EXPECTED_SHA)
```

Вывод тем же кодом, что работает в приложении:

```
релизный libkenji.so: выравнивание = 16 КБ
страницы 4 КБ  → подходит
страницы 16 КБ → подходит
```

То есть **сам файл ядра совместим и с 4-КБ, и с 16-КБ страницами**, и лишних зависимостей
(вроде .NET-рантайма) у него нет. Значит отказ, если он был, приходил не от «ядро не подходит
к телефону», а от кнопки и от загрузки в процессе — это и исправлено.

### Запасной путь: как в оригинале

Если своё ядро не готово, а официальный APK Kenji установлен, игра не уходит молча на Eden:

* на экране «Два ядра» есть кнопка «Играть через Kenji»;
* на плитке игры, поставленной на второе ядро, запуск отдаётся официальному приложению —
  с сообщением, почему (Snackbar: «Открыл игру в «Kenji»: своё ядро не готово (…)»).

## 15. Обложки, сейвы и облако

### Почему в нативной библиотеке были только буквы

`LauncherTileAdapter` **никогда не запрашивал обложку**: в `bind()` рисовалась монограмма
(буква в цветном квадрате) и всё. Загрузчик `GameIconUtils` в приложении был — им пользуется
штатный список игр и ярлыки на рабочем столе, — но нативная плитка к нему не обращалась.
Поэтому «в WebView обложки есть, а тут квадратики» было не «не грузится», а «никто не
просил».

Теперь: в плитке `ImageView` под монограммой; картинка запрашивается по той же модели `Game`
и из того же кэша Coil, что и в штатном списке. Ответ асинхронный, поэтому ячейка помечается
путём игры — обложка от прошлой строки не попадает в соседнюю. Если иконки нет (homebrew,
битый заголовок, нет ключей) — картинка прячется и остаётся буква, а не серая заглушка.

### Сейвы: что показывается и что измеряется

`SavesOverview` считает по файлам: сколько слотов, сколько весит, когда создан, когда
последнее сохранение, сколько дней не заходили, сколько времени прошло **с самого
сохранения**. Последнее — ответ на исходную жалобу «десять часов на миссии и ничего не
добился»: видно, что игра не сохранялась двенадцать часов.

Проверки: `SavesOverviewTest` — **56/0**. Отдельно закрыты случаи, на которых строки врут:
«0 дней назад» вместо «не запускалась», «только что» при отсутствии сохранений, склонение
«21 день» (в первой версии было «21 дней» — тест поймал).

### Процент прохождения: почему вручную

Настоящий процент лежит внутри сейва в формате конкретной игры, часто сжатом. Вывести его
из размера папки или числа файлов нельзя. Автоматическая «оценка» была бы выдумкой, а
выдуманный прогресс хуже отсутствующего: по нему решают, начинать ли заново. Поэтому процент
ставит человек (`ProgressMarks`, кнопки 0–100), и экран говорит это прямым текстом.

### Облако: WebDAV

Почему не Google Drive: он требует OAuth-клиента, зарегистрированного в консоли разработчика —
без него кнопка «войти» не работает ни у кого, кроме владельца проекта. WebDAV работает с
логином и паролем приложения и поддерживается Яндекс.Диском, Nextcloud, Box, Облаком Mail.ru
и домашним сервером.

| Часть | Что делает | Проверка |
|---|---|---|
| `WebDavParse` | разбор `207 Multi-Status`, сборка и кодирование путей, даты RFC 1123 | `WebDavParseTest` **37/0** |
| `WebDavClient` | PROPFIND / MKCOL / PUT / GET / DELETE, отказы словами | требует сети, на хосте не проверяется |
| `CloudSync` | слоты сейвов по профилям, заливка/скачивание по файлам, образы по кнопке | — |

Правила, заложенные в код:

* **скачивание не затирает более свежий локальный сейв** — уже стирало прогресс людям;
* **образы не заливаются автоматически** — это гигабайты и мобильный трафик;
* **`download` пишет в `.part` и переименовывает** — оборванная загрузка не оставляет
  полуфайл на месте целого;
* **отказ — фразой**, без имён исключений: «сервер не найден», «логин или пароль не подошли».

### Чего здесь нет и почему

Запуска игры «прямо из облака» нет. Эмулятору нужен локальный файл и десятки тысяч
произвольных чтений по гигабайтному образу — по сети это не «медленно», а невозможно.
Схема честная: скачать → играть → сохранения уходят обратно.

## 16. Распаковка NSZ / XCZ / NCZ: формат, а не догадка

**Жалоба:** «конвертация — ошибка, выдал ноль результата», «неправильно устроен».

**Что было не так.** Две независимые ошибки, каждая из которых делает распаковку
невозможной:

1. таблица секций читалась по смещению `+16` вместо реального `0x4000 + 8 + 8`, а число
   блоков — из `meta[12..15]`, которого в формате нет; блоки и сплошной поток после этого
   разбирались как попало;
2. шифрование секций не возвращалось: в NCZ тело секции лежит **расшифрованным**, и
   AES-128-CTR с ключом и счётчиком из таблицы должен быть применён на выходе. Без этого
   получался «правильный» поток и нерабочий NCA.

Плюс отдельно: у образов XCI корневой раздел HFS0 лежит по фиксированному смещению
**0xF000**, а код считал его как `u64` из `0x130`, умноженный на `0x200` — то есть искал
не там. Это ломало и «сохранить как NSP» для обычного XCI.

**Что сделано.** Разбор переписан по эталонной раскладке (nsz / SAK), отдельным модулем
`patch/symbiosis/ncz.cpp`:

| Часть | Правило |
|---|---|
| заголовок | 0x4000 байт копируются как есть |
| таблица | `NCZSECTN`, `u64` число секций, по 0x40 байт: смещение, размер, тип шифрования, ключ, счётчик |
| блоки | `NCZBLOCK`: версия, тип, `u8` экспонента размера, `u32` число блоков, `u64` размер, `u32[]`; блок меньше размера блока — zstd, иначе как есть |
| сплошной поток | один zstd-поток на все секции |
| шифрование | типы 3 (CTR) и 4 (BKTR) → AES-128-CTR по абсолютному смещению в NCA |
| AES | своя реализация `patch/symbiosis/aes128.cpp`: `core/crypto` из common недоступен (циклическая зависимость) |

zstd берётся из дерева Eden (`AddJsonPackage(zstd)` + `zstd::zstd` в `src/common`), свой
декодер не вендорится: рядом живёт `zstd_compression.cpp`, и второй набор символов `ZSTD_*`
сломал бы линковку.

**Проверка.** `tests/t_nsz.cpp` — 17 проверок:

| Что | Как |
|---|---|
| AES-128 | векторы FIPS-197 C.1 и B.1, CTR сверен с `openssl` |
| solid NCZ, секция BKTR | распаковка, сравнение байт в байт |
| NSZ: сжимаемая секция + несжимаемая + дырка между секциями + обычный NCA | извлечение файлов из NSP, сравнение |
| XCZ: корневой HFS0 в 0xF000, раздел secure | извлечение файлов из NSP, сравнение |
| обрезанный файл | ноль байт, понятная причина, недописанный выход удалён |

Файлы для теста собирает `tests/data/make_fixtures.py` — **отдельной реализацией того же
формата** (Python, настоящие `zstandard` и `pycryptodome`). Если бы и генератор, и
распаковщик писались по одной и той же ошибке в голове, тест подтверждал бы только
согласованность ошибки с самой собой.

`tools/run_tests.sh` требует `libzstd-dev` и без него останавливается: молчаливый пропуск
теста распаковки — ровно то, из-за чего «ноль байт» доехал до телефона.

**Чего это не проверяет.** Настоящий образ на 15 ГБ в CI не прогоняется — тест на
синтетических файлах того же формата. Поэтому первая же проверка на телефоне — на реальном
скачанном NSZ.

## 17. Дубликаты, обложки и журнал ядра

### Дубликаты игр (жалоба: «выбрал подпапку — появились дубликаты»)

Один файл приходит с разными URI, если добавить и `Games`, и `Games/Switch`:

```
…/tree/primary%3AGames/document/primary%3AGames%2FSwitch%2Fgame.nsp
…/tree/primary%3AGames%2FSwitch/document/primary%3AGames%2FSwitch%2Fgame.nsp
```

`distinctBy { it.path }` сравнивал строки целиком — они разные, поэтому появлялись две
плитки. Ключ теперь — идентификатор документа (`GameFolderList.fileKey`), то есть часть
после `/document/`. Регистр не приводится: на внутренней памяти `Game.nsp` и `game.nsp` —
разные файлы.

Проверка: `GameFolderListTest` **40/0** (было 34/0).

### Обложки (жалоба: «по-прежнему съезжают»)

Три причины, все в загрузчике:

1. **Не отменялся прошлый запрос.** Coil рисует картинку в `ImageView` сам, как только она
   готова. Запрос прошлой игры не отменялся и приходил позже нового — поверх обложки
   соседа. Проверка метки в колбэке этого не ловит: картинка уже нарисована. Теперь старый
   запрос отменяется (`GameIconUtils.inflight`), а `onViewRecycled` отменяет и очищает.
2. **Метку ставил загрузчик, а не адаптер.** При любом раннем выходе из загрузчика в
   ячейке оставалась метка прошлой игры, и запоздавший ответ считался «своим». Теперь метка
   ставится при привязке ячейки, до обращения к загрузчику.
3. **Заглушка считалась успехом.** Фетчер возвращал `default_icon` как успешный результат:
   Coil клал её в кэш по пути файла, экран показывал картинку вместо буквы, и после смены
   ключей из кэша доставалась та же заглушка. Теперь отсутствие обложки — отказ: остаётся

## 19. Ровность кадров и звук: «60 → 15 → 45 → 5» и треск в аркадах

Жалоба дословно: «звуковые эффекты и музыка с тормозами, когда анимации стабильны,
а в Zelda наоборот — звук ровный, а кадры прыгают с 60 на 15, потом на 20-45, потом на 5».

Это две разные болезни с одинаковым симптомом «лагает», и лечатся они
противоположно. Поэтому экран сначала **измеряет**, а потом советует: без чисел
«попробуйте выключить vsync» — это гадание.

### Что сделано

| Слой | Где | Что даёт |
|---|---|---|
| счётчики в движке | `patch/symbiosis/frame_metrics.{h,cpp}` | длительность каждого системного кадра (мкс), провалы аудио, сборки конвейеров; кольцо на 1024 кадра, атомики, без блокировок |
| хунки в Eden v0.2.1 | `perf_stats.cpp` `EndSystemFrame`, `sink_stream.cpp` (ветка `!queue.TryPop`), `vk_pipeline_cache.cpp` (`if (is_new)`), `oboe_sink.cpp` (`SymbiosisAudioBufferFrames`) | счётчики питаются настоящими событиями, а не таймером |
| настройка буфера звука | `settings.h` `symbiosis_audio_buffer_ms` (20 мс, 10…100) | Eden кладёт в буфер Oboe `TargetSampleCount*2` = 10 мс; на части устройств это меньше, чем задержка планировщика |
| JNI | `native_symbiosis.cpp` `frameMetrics` / `resetFrameMetrics` | снимок строкой, одна граница на всё |
| разбор снимка | `FrameMetricsText.kt` | мусор и пустой ответ не роняют экран |
| анализ | `FramePacing.kt` | доли частоты экрана, шейдерные паузы, тепловой сброс |
| экран | `PerformanceFragment` («Инструменты» → «Ровность кадров») | медиана / 90% / худшие 1% / худший кадр, причина, советы, чипы звука 10/20/30/50 мс, копирование отчёта |

### Как читаются числа

- **60 → 30 → 15** (ровно доли частоты) — упор в вертикальную синхронизацию.
  `vk_swapchain.cpp` при FIFO ждёт следующего кадра целиком: не успел на 1 мс —
  потерял 16. Такое поведение выглядит как «прыгает с 60 на 15», хотя GPU нагружен
  наполовину.
- **Медиана низкая, отдельные кадры в разы дольше** — сборка шейдера в кадре
  (`use_asynchronous_shaders=false` в v0.2.1 = сборка в потоке отрисовки).
  Лечится проходом по тому же месту и асинхронными шейдерами.
- **Ровно, потом вдвое хуже и не возвращается** — тепловой сброс частот;
  турбо-режим в этот момент делает хуже.
- **Звук при ровной картинке** — буфер 10 мс и повтор последнего кадра в
  `sink_stream.cpp`; лечится 20–30 мс, а не настройками графики.

## 20. «Распаковка закончилась без результата» и «мост упал в :kenji»

Два отчёта с устройства (itel S666LN, Android 13, 4 КБ страницы), оба — про
места, где приложение знало причину отказа и не говорило её.

### 20.1. Распаковка

Уведомление выглядело так: **«Распаковка закончилась без результата. Файлы
здесь: /storage/emulated/0/Download/Symbiosis»**. Причина в этом тексте
отсутствовала по построению: `ConverterService.finish()` выбирал текст по
одному признаку — «есть ли путь», — а путь есть всегда.

| Что было | Чем грозило |
|---|---|
| при отказе показывался путь вместо причины | «без результата» без единой подсказки, что чинить |
| формат определялся по расширению | `.zip` (и `.nsz`, переименованный из zip) уходил в нативную распаковку |
| отказ нативной части приходил как «Not an NSZ…» и схлопывался в «распаковка не удалась» | не отличить архив от битого образа |
| временный каталог брался из `std::filesystem::temp_directory_path()` | на Android `TMPDIR` не выставлен, `/tmp` нет → исключение в JNI, то есть `abort` |

Что сделано:

- `RomSniff` — определение контейнера по **первым байтам**: ZIP `50 4B 03 04`,
  RAR `52 61 72 21`, 7z, GZ, `HEAD` (XCI/XCZ), `PFS0` (NSP/NSZ), `NCA*`
  (NCA/NCZ), `NRO0`. Расширение — только запасной признак, когда подпись
  переставлена. Архивы и мусор отсекаются до копирования большого файла.
- `RomTools::SetWorkDir` + `NativeSymbiosis.setRomWorkDir`: рабочий каталог
  приходит из Kotlin (кэш приложения); если он не задан — `try/catch` вокруг
  `temp_directory_path()` и запасной вариант рядом с результатом. Отсутствие
  каталога больше не «не удалось», а `No writable work directory: <путь>`.
- `ConverterReasons.outcomeText` — причина первой строкой, путь второй.
- Новые фразы причин: «это не сжатый образ», «некуда распаковать», «не удалось
  скопировать файл в папку результата».

### 20.2. Второе ядро

Окно «Почему не запустилось» выдавало заранее написанный текст: **«наш мост
упал в :kenji — это не «телефон не тянет». Официальный Kenji на этом
устройстве уже играет»**. Вторая половина — утверждение, которого никто не
проверял; оно отправляет человека искать проблему не там.

Процесс `:kenji` умирает от сигнала, и Android не отдаёт приложению ни номера
сигнала, ни стека — только `onServiceDisconnected`. Поэтому теперь причина
записывается **до** смерти процесса, в файл, который её переживает:

| Слой | Что пишет |
|---|---|
| `libsymbiosis_kenji.so`, обработчик `SIGSEGV/SIGBUS/SIGILL/SIGFPE/SIGABRT` | `step=…`, `crash signal=… name=… addr=… code=…`, до 12 кадров `pc=<библиотека>+0x…` |
| `debug_break(int)` в мосте | `debug_break=<код>` — ядро само сообщает об ошибке инициализации |
| метки `NoteStep` в JNI | шаг ставится перед вызовом: `dlopen`, `javaInitialize`, `deviceInitialize`, `graphicsInitialize`, `attachSurface`, `deviceLoadDescriptor`, `graphicsRendererRunLoop` |

Обработчик после записи восстанавливает `SIG_DFL` и повторяет сигнал: приложение
не глотает падение, tombstone у Android остаётся настоящим. `KenjiCrash`
разбирает файл и `KenjiCrash.verdict` разделяет два разных вывода — «падение
внутри `libkenji.so`» (чинить файл ядра) и «падение в нашей части моста».

  хосте: `child_signalled=1 signal=11`, в файле `step=javaInitialize`,

### 20.3. Первый настоящий отчёт с устройства и что в нём было не так

Отчёт пришёл (это уже плюс: раньше на этом месте была догадка):

```
шаг: javaInitialize · сигнал: 6 (SIGABRT) · адрес: 0x2e5300005fb0
верхние кадры: libsymbiosis_kenji.so+0x2b968 → [vdso]+0x89c → libc.so+0x530f4
```

Что из него следует и что пришлось починить:

| Наблюдение | Причина | Что сделано |
|---|---|---|
| верхний кадр — наша же библиотека, ниже `[vdso]` | `_Unwind_Backtrace` из обработчика сигнала не проходит через сигнальный кадр: первый кадр — сам обработчик | кадры снимаются из `ucontext`: pc + цепочка x29 (frame pointer), первый кадр теперь настоящий адрес падения |
| вывод «Падение внутри libkenji.so» при кадрах из нашего .so | вердикт строился по принципу «есть ли `libkenji.so` где-нибудь в стеке» | вердикт смотрит на **верхний** кадр; добавлены отдельные выводы для «вне обеих библиотек» |
| `SIGABRT` объяснялся как обычное падение | это не сбой памяти, а `abort()` | отдельная строка про `abort()` и про то, что у .NET-ядер так заканчивается необработанное исключение |
| текста исключения нет | его печатает рантайм в журнал системы, а не в наш отчёт | после падения читается `logcat -d` (только свой UID), из него берутся строки про исключение/failfast и прикладываются к отчёту |

Сам `SIGABRT` на шаге `javaInitialize` означает: файл ядра загрузился и был
проверен по символам, но **сам код ядра остановился** при передаче ему путей и
JNI. Номер блока и текст исключения появятся в следующем отчёте — тогда и будет
видно, чинить файл или мост.

### 20.4. Распаковка: что добавилось после второго снимка

Второй снимок показал, что причина уже называется («сжатые данные внутри файла
повреждены»), но не сказано, **какой файл**. Добавлено:

- имя файла в первой строке уведомления: `«Zelda.nsz»: …`;
- файл `Download/Symbiosis/последняя-ошибка.txt` — имя, размер, определённый
  формат, первые байты в hex, **дословный ответ ядра** (например `Block 12 is
  damaged: Data corruption detected`) и перевод. Это ответ на вопрос «файл битый
  или это баг распаковщика» без чтения журналов.

### Чего здесь по-прежнему нет

Причина падения второго ядра на этом телефоне **ещё не установлена**: отчёт
появится только в следующей сборке, и по нему будет видно, чинить файл ядра
или мост. Утверждений вида «на этом устройстве играет» в приложении больше нет.

## 21. Быстрые настройки в игре и третий отчёт с устройства

Жалоба дословно: «в оверлее выбор настроек под каждую игру особо ничего не
меняет, их там мало, нет точного применения настроек, я их включил, но в игре
ничего не поменялось; качество поменять не могу; звуковое устройство не могу
сменить во время эмуляции».

Обе половины жалобы — про одно и то же, и обе верны.

### 21.1. Почему «ничего не поменялось»

Стандартная панель Eden умеет десять пунктов, и в ней нет ни разрешения, ни
звука. А те пункты, что есть, ядро читает в разные моменты:

| Настройка | Где читается | Вывод |
|---|---|---|
| `resolution_setup` | `VideoCore::Init` → `Settings::UpdateRescalingInfo` | только при запуске |
| `use_vsync` | `ChooseSwapPresentMode` при создании swapchain | только при запуске |
| `output_engine` | при создании звукового вывода | только при запуске |
| `symbiosis_audio_buffer_ms` | при создании звукового потока | только при запуске |
| `audio_volume` | применяется к сессиям на ходу | сразу |
| `speed_limit` | читается каждый кадр | сразу |

То есть настройки работали — но не в тот момент, когда человек ждал, и никто
ему об этом не сказал. Вывод, к которому он пришёл («настройки не работают»),
был логичным.

### 21.2. Что сделано

- `QuickPanel` — таблица «сразу / после перезапуска» с указанием, **почему** так
  (по месту в коде ядра). Под каждым пунктом панели стоит подпись, внизу —
  строка вида «Применено сразу: 1. Ждут перезапуска игры: 2.».
- В панель добавлено то, чего не было: **разрешение**, **вертикальная
  синхронизация**, **звуковой движок**, **буфер звука** (чипы 10/20/30/50 мс),
  **громкость** (ползунок, байтовая настройка `volume`).
- Кнопка **«Перезапустить игру»**: сохраняет глобальную и игровую конфигурацию,
  останавливает эмуляцию и запускает ту же игру заново. Показывается только
  тогда, когда действительно есть что применять.
- Громкость читается и пишется как `ByteSetting.AUDIO_VOLUME`: через `getInt`
  по ключу `volume` вернулся бы 0, и ползунок показывал бы тишину.

### 21.3. Третий отчёт о падении второго ядра

```
шаг: javaInitialize · сигнал: 6 (SIGABRT) · адрес: 0x2e53000005a6
кадры: libc.so+0x530f4 → libc.so+0x530c8 → libkenji.so+0x173c214
```

Кадры теперь настоящие (первый — `abort()` в libc, второй — `raise()`,
третий — код ядра). Из этого следует точный вывод, и он теперь так и
формулируется: **`abort()` вызван изнутри libkenji.so** — ядро загрузилось и
прошло проверку символов, но само остановилось при передаче ему путей и JNI.
Вердикт больше не путает «механизм» (libc) с «виновником»: libc, libm, libdl и
`[vdso]` пропускаются при выборе виновного кадра.

Что добавлено для следующего шага:

- читается **буфер крашеи** `logcat -b crash -d` — там Android хранит tombstone
  с `Abort message`, то есть текстом исключения .NET. В общем буфере его нет:
  он вытесняется за секунды, и в предыдущем отчёте поэтому были только адреса;
- строки `Abort message`, `signal 6`, `exception:` поднимаются в начало выборки.

### 21.4. «Журнал ядра» показывал 0 КБ

Файл `eden_log.txt` существовал и был пуст, а экран советовал «запустите игру» —
совет, который уже не помогал. Теперь:

- пустой файл отличается от отсутствующего: «файл создан, но пуст — свой
  файловый журнал включается отдельно от системного»;
- добавлен источник **«система»**: `logcat -d` того же приложения. Он пишется
  всегда и содержит старт ядра, отметки SymbiosisKenji и fatal-строки.

### Проверка

- `tests/QuickPanelTest.kt` — 26 проверок таблицы: что применяется сразу, что
  после перезапуска, строка состояния, подсказки по буферу, наличие объяснения
  у каждого отложенного пункта.
- `tests/KenjiCrashTest.kt` — 48 проверок, включая разбор настоящего отчёта с
  устройства: libc не обвиняется, вывод «abort() вызван изнутри libkenji.so»,
  `Abort message` попадает в выборку из журнала.
- Весь набор — **47/0**; патч целиком применяется к Eden v0.2.1
  (`PATCH_APPLIED files=188`), проверки Kotlin/JNI/строк — 0 проблем.

### Чего здесь по-прежнему нет

Причина `SIGABRT` в самом ядре **ещё не названа**: для этого нужен `Abort
message` из буфера крашеи, а он появится только в следующей сборке. Ни один
экран не утверждает, что ядро запустится: он говорит, на каком шаге оно
остановилось и почему это не «телефон не тянет».

## 22. Третий отчёт: битый NSZ, чужой журнал и падение с открытой панелью

Три жалобы из одного сообщения, и у каждой своя причина — ни одна не была
«файл плохой» или «телефон не тянет».

### 22.1. Твёрдый NSZ объявлялся повреждённым — виноват zstd, не файл

Файл «Vault of Power [01004F302847E000][v0] (0.31 GB).nsz» отвергался с
сообщением о повреждённых сжатых данных. Формат тут не при чём: наш разбор
NCZ (`patch/symbiosis/ncz.cpp`) соответствует описанию контейнера —
заголовок, секции по 0x40 байт, блоки `NCZBLOCK` по 24 байта и таблица
размеров. Ошибку выдал сам декодер, `ZSTD_getErrorName` даёт ровно
«Data corruption detected».

Причина — пин zstd. В Eden v0.2.1 `cpmfile.json` держит zstd на `b8d6101fba`
(1.5), а в этой версии включена оптимизация ветвления в
`ZSTD_decodeSequence`, которая на ARM64 считает неверно и портит данные.
Upstream Eden исправил это сменой пина на `33618c8` — версию с отменённой
оптимизацией (коммит «Support block-compressed NSZ and XCZ»).

Что сделано:

- `tools/apply_patch.sh` поднимает пин в `cpmfile.json` до `33618c8` и
  проверяет результат: без этого шага `grep '"33618c8"'` валит сборку, потому
  что иначе любой правильный NSZ снова будет «битым»;
- в `docs/GUIDE.md` §16 добавлен абзац: сообщение о повреждении больше не
  означает «скачайте заново», и что делать, если оно всё-таки появилось.

Поля задаются в форме, которую понимает `CPMUtil` именно v0.2.1. В master
Eden достаточно `version` + `hash` (там `version` сама служит ссылкой на
коммит), а `CPMUtil` v0.2.1 ищет `TAG`, `SHA` или `BRANCH`: на голый
`version` он пишет «REPO defined but no TAG, SHA, BRANCH, or URL» и уходит на
master zstd, где скачивание падает. Это и случилось в прогоне `41327290304` —
сборка легла на `zstd-populate`. Поэтому `sha` задаётся явно, и хеш
проверен не на слово: sha512 архива `github.com/facebook/zstd/archive/33618c8.tar.gz`
совпадает с `2b006c3c…`.

Проверено: на свежем клоне v0.2.1 `PATCH_APPLIED files=190`, блок `zstd` в
`cpmfile.json` — `sha 33618c8`, `version 33618c8`, `min_version 1.5`, хеш
`2b006c3c…`; этот же блок отдельно прогнан на копии исходного файла.

### 22.2. Журнал в отчёте был от другого процесса

В отчёте стояли строки PID 4628, а процесс к тому моменту имел 24319:
`logcat -d -t 400` без фильтра отдаёт хвост общего буфера, куда попадают
записи уже закрытых процессов того же приложения. Такой журнал не просто
бесполезен — он указывает не на ту причину.

- `KenjiCrash.logcatArgs(pid, buffer, lines)` — аргументы с `--pid`;
- `KenjiCrash.filterByPid(text, pid)` — повторная фильтрация по колонке PID
  (строки без даты, то есть продолжения многострочных сообщений, наследуют
  решение предыдущей записи);
- служба живёт в `:kenji`, поэтому `Process.myPid()` — это PID упавшего ядра;
- если журнала своего процесса нет, отчёт говорит это прямо, а не молчит.

### 22.3. Текст исключения .NET — из файла, а не из журнала

В отчёте о сигнале есть адреса, но нет текста. Теперь `ArmStdioCapture()` в
мосте перенаправляет stdout и stderr процесса `:kenji` в
`kenji-stdout.txt` рядом с отчётом, без буферизации (процесс умирает до
`fflush`). `KenjiCrash.exceptionLines` достаёт оттуда строки про исключение и
кадры стека, и они идут в отчёте первым блоком — «Что сказало ядро перед
остановкой».

### 22.4. Падение при открытой панели быстрых настроек

Причина в самом устройстве панели: на каждое изменение вызывался
`addQuickSettings()`, то есть `removeAllViews()`, — из обработчика того
элемента, который в этот момент удалялся с экрана (у радиокнопки из её
`setOnCheckedChangeListener`, у чипа буфера из `onClick`). Плюс каждый цвет
брался через `MaterialColors.getColor`, который бросает исключение, если
атрибута нет в теме.

- панель не пересобирается: `quickPanelRefresh` обновляет тексты, подсветку
  чипов и видимость кнопки перезапуска;
- кнопка «Перезапустить игру» создаётся всегда и только показывается;
- цвета берутся через `quickColor(...)` — по порядку атрибутов, с запасным
  оттенком вместо исключения;
- всё тело панели под `try/catch`: ошибка в одном пункте пишется в журнал и
  показывается строкой, а не закрывает игру;
- `UiGuard` ставит обработчик необработанных исключений в
  `EmulationActivity.onCreate` и пишет их в `symbiosis/ui-crash.txt`
  (`KenjiCrash.describeThrowable` — время, поток, тип, стек). Нативный сбой
  ядра идёт мимо него, своим отчётом.

### Проверка

- `tests/KenjiCrashTest.kt` — **70 проверок, 0 падений**: к ним добавились
  разбор stderr-файла (исключение, внутренняя причина, кадры, отброс шапки),
  фильтр по PID (чужая строка отброшена, продолжение своей — оставлено) и
  формат записи необработанного исключения.
- C++ мост: `ArmStdioCapture` и `InstallCrashHandlers` проверены на хосте
  настоящим `SIGSEGV` — файл stderr создан, строка `Unhandled exception.`
  в нём, в отчёте есть `step=` и кадры `pc=`.
- Весь набор хоста — **11/0, skipped=12**; патч на свежем v0.2.1 —
  `PATCH_APPLIED files=190`; `check_kotlin_refs` — 104 файла, 0 проблем;
  `check_jni_names` — 76, 0 проблем; `check_string_refs` — 1484 строки.

### Чего здесь по-прежнему нет

Распаковка после смены пина **на устройстве ещё не проверена** — вывод «файл
теперь читается» будет только после прогона с тем же NSZ. Причина `SIGABRT`
внутри ядра тоже не названа: теперь для неё есть текст из stderr, но он
появится в следующем отчёте, а не задним числом.
